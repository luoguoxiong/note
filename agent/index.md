# LLM Agent

## Q1: 你如何定义一个基于 LLM 的智能体（Agent）？它通常由哪些核心组件构成？

### 定义

一个基于 LLM 的智能体是以 **LLM 作为决策核心（大脑）**，在一个反馈循环中**自主感知环境、规划任务、调用工具并执行行动**，以达成给定目标的系统。

区别于普通 LLM 应用（单次调用、固定流程），Agent 的本质特征是：**执行路径不是预先写死的，而是由模型在循环中动态决定**。

> Agent = LLM（大脑）+ 规划 + 记忆 + 工具

### 核心组件

| 组件 | 职责 | 典型实现 |
|------|------|----------|
| **LLM 核心** | 推理与决策中枢，理解目标、选择下一步动作 | GPT/Claude/GLM 等，支持函数调用 |
| **规划（Planning）** | 任务分解、子目标拆解、反思与重试 | CoT、ReAct、Reflexion、Plan-and-Execute |
| **记忆（Memory）** | 短期：当前对话上下文；长期：跨会话知识 | 上下文窗口、向量数据库 + RAG、摘要压缩 |
| **工具（Tool Use）** | 突破文本局限，与外部世界交互 | Function Calling、MCP、API、代码执行器、搜索 |
| **Agent 循环** | 感知 → 思考 → 行动 → 观察结果 → 再决策 | ReAct 式 loop，含终止条件与最大步数 |
| **约束与防护** | 权限控制、敏感操作确认、防幻觉防死循环 | Guardrails、审批机制、系统提示词 |

### 关键理解（加分点）

- **Agent 与 Workflow 的分界**：Workflow 由代码预先编排 LLM 调用节点（路径固定）；Agent 由 LLM 自己决定调用什么、按什么顺序（路径开放）。两者常混合使用——用 Workflow 保证可控性，在关键节点嵌入 Agent。
- **有效性瓶颈往往不在模型，而在上下文工程**：给循环中持续注入正确的状态、历史和工具结果，比提示词技巧更决定成败。
- **最小可行 Agent 只需三样**：一个循环（`while 未完成: 让 LLM 决策并执行`）、一组工具、一个终止条件。其余组件（记忆、规划框架）都是在此骨架上的增强。

## Q2: 详细解释 ReAct 框架。它是如何将思维链和行动结合起来，以完成复杂任务的？

### 解决什么问题

| 范式 | 做法 | 缺陷 |
|------|------|------|
| 仅推理（CoT） | 生成思维链后直接给答案 | 无法获取新信息，事实靠"脑补"，易幻觉 |
| 仅行动 | 直接调用工具返回结果 | 无推理引导，不会规划多步、不会利用参数化知识 |
| **ReAct** | 推理与行动交错 | 两者互补：推理引导行动，行动结果修正推理 |

### 工作循环

每轮由 LLM 生成 Thought 和 Action，Observation 由环境注入：

```
Thought（推理）  →  我现在知道什么？下一步该做什么、为什么？
Action（行动）   →  选择工具 + 参数
Observation（观察） → 工具执行结果（外部环境返回，非模型生成）
        ↓ 循环
...  →  Thought: 有了新信息，重新评估 → Action → ... → Final Answer
```

### 如何把思维链和行动结合起来（核心）

1. **思维链"外化"**：CoT 的每步推理只能依赖参数里的知识；ReAct 允许某一步推理结论是"我不知道，去查"，于是推理自然产生一次工具调用，用真实 Observation 替换凭空推断。
2. **推理为行动提供依据，行动为推理提供事实**：Thought 决定调哪个工具、传什么参数；Observation 反过来更新下一轮 Thought 的前提，形成"计划 → 执行 → 校准"的闭环。
3. **错误可恢复**：Observation 不符合预期时（搜索无结果、报错），下一条 Thought 会显式反思并换策略——这是固定流水线做不到的。

### 示例（多跳问题）

> 问：华盛顿去世那年，《XX》的导演几岁？

```
Thought 1: 需要先确定华盛顿去世年份
Action 1:  Search[华盛顿 去世年份]     → Obs 1: 1799 年
Thought 2: 下一步查该导演是谁
Action 2:  Search[电影 XX 导演]        → Obs 2: 导演 A
Thought 3: 查 A 的出生年份，1799 − 出生年即答案
Action 3:  Lookup[A 出生]              → Obs 3: A 生于 1750
Thought 4: 1799 − 1750 = 49，可作答
Action 4:  Finish[49]
```

复杂任务之所以能完成：**Thought 把大问题拆成子问题，每个子问题对应一次工具调用；Observation 逐个消解子问题，直到推理链闭合**。

### 局限与演进（加分点）

- **错误累积**：一步 Observation 误导，后续整条轨迹可能跑偏 → 衍生出 Reflexion（自我反思重试）、Self-Consistency（多轨迹投票）。
- **不是所有任务都该 ReAct**：纯数学推理不需要外部事实，加行动反而引入噪声，实验中纯 CoT 有时更好。
- **现代形态**：Function Calling 普及后，Thought 常被模型内化（不可见），但"推理 → 调用 → 观察"的骨架不变；LangChain/LlamaIndex 的 ReAct Agent、各类 Agent Loop 本质都是它的工程化变体。
- **安全注意**：Observation 来自不可信外部，可能被注入恶意指令劫持 Agent（间接 prompt injection）。

## Q3: CoT、ToT、GoT、ReAct 的区别？

### 一句话定位

前三者是纯推理的**拓扑结构演进**（链 → 树 → 图），ReAct 换了维度——**把推理接上行动和外部环境**。

### 四者概览

| | 结构 | 核心机制 | 外部交互 | LLM 调用成本 | 典型适用 |
|---|------|----------|----------|--------------|----------|
| **CoT** (2022) | 线性链 A→B→C→D | "Let's think step by step"，逐步推理 | 无 | 1 次 | 一般推理题 |
| **ToT** (2023) | 树（分支 + 回溯） | 每步生成多个候选想法，评估器打分，BFS/DFS 搜索并剪枝 | 无 | 多倍 | 需探索/规划的谜题（24 点、填字） |
| **GoT** (2023) | 图（可合并） | 想法节点可合并（merge）、聚合、精炼，两条推理线汇合成新节点 | 无 | 高 | 可分解又需综合的任务（排序、多段摘要） |
| **ReAct** (2022) | 线性思维链 + 行动循环 | Thought → Action → Observation 循环 | **有**（工具/环境） | 每步 1 次 | 需要外部事实/工具的任务 |

### 关键区别

1. **CoT 的根本缺陷 → ToT 的动机**：CoT 是单路径顺序生成，第 3 步错了整条链报废，无法回溯。ToT 把推理建模成树搜索：一个节点走不通就退回父节点换分支，用全局视野代替"一条道走到黑"。
2. **ToT 的根本限制 → GoT 的动机**：树只能父子相连，两条有价值的推理线无法**合并**。GoT 允许任意节点互联（如把 B₁ 和 C₂ 的结论聚合出新节点 D），表达能力和可做的问题类型都更广。
3. **ReAct 与前三者正交**：CoT/ToT/GoT 都在参数化知识里"闭门推理"，不产生新信息；ReAct 每一步可以"我不知道，去查"，用工具结果喂给下一轮推理，解决的是**事实性/交互性**问题，而非推理搜索问题。
4. **纠错方式不同**：ToT 靠搜索回溯（事前避免）；ReAct 靠观察反馈后的反思修正（事后补救，线性推进不回溯）。

### 组合关系（加分点）

- 四者**正交、可叠加**：一个 Agent 的主循环是 ReAct，其中某一步 Thought 内部做 CoT；规划复杂决策时，可以嵌一个 ToT 搜索作为该步的"大脑"。
- 直观类比：CoT 是走一条路，ToT 是带地图和评分探索岔路，GoT 是多人分头探索后合并情报，ReAct 是边走边问路。
- 成本递增：CoT < ReAct < ToT ≈ GoT，实际系统很少整体上 ToT/GoT，多为"关键节点局部使用"。

## Q4: 如何为 Agent 设计短期记忆和长期记忆系统？可以借助哪些外部工具或技术？

### 1. 先建立记忆分类框架

| 类型 | 内容 | 载体 |
|------|------|------|
| **短期记忆（工作记忆）** | 当前任务的对话历史、中间结果 | 上下文窗口 |
| **长期记忆 - 情景记忆** | 具体发生过的事（历史对话、任务轨迹） | 向量库/数据库 |
| **长期记忆 - 语义记忆** | 提炼出的事实、用户偏好、世界知识 | 向量库/结构化存储/知识图谱 |
| **长期记忆 - 程序性记忆** | "怎么做事"：工具用法、成功经验、教训 | System prompt / 技能库 / 文件 |

### 2. 短期记忆设计：本质是管理上下文窗口这个稀缺资源

- **滑窗截断**：保留最近 K 轮，最简单但会丢早期关键信息。
- **滚动摘要**：旧历史压缩成 summary 放前面 + 最近原文，长任务标配。
- **结构化状态替代原始对话**：不囤聊天记录，维护一份 scratchpad / todo list / 任务状态，每步由 Agent 更新——信息密度远高于原文。
- **工具结果分级处理**：旧工具结果（如整个网页）及时替换为摘要，只保留关键结论。
- **外置到文件**：把重要状态写入工作区文件，需要时再读回（Claude Code 式做法），突破窗口限制。

### 3. 长期记忆设计：核心是四个环节

```
写入 → 存储 → 检索 → 更新/遗忘
```

- **写入**：决定"什么值得记"。两种策略：全量入库靠检索过滤（简单但噪声大） vs 由 LLM 判断重要性再写（需写入门控）。时机上分实时写入与会话结束离线提炼。
- **存储**：按记忆类型选形态——对话片段进向量库；用户画像/偏好用结构化 KV；实体关系用知识图谱。
- **检索**：混合检索（向量语义 + BM25 关键词 + 元数据过滤）→ reranker 重排 → 注入 prompt。关键在**检索时机与预算**：不是越多越好，注入无关记忆反而干扰。
- **更新/遗忘**：最容易被忽视但最难。新信息与旧记忆冲突时要做合并/覆盖决策；配合重要性评分、时间衰减做遗忘；定期把零散记忆"巩固"成抽象知识（reflection）。

### 4. 可借助的外部工具/技术

| 环节 | 工具 |
|------|------|
| 向量数据库 | Chroma（本地轻量）、Qdrant、Milvus、Weaviate、Pinecone、pgvector（复用 Postgres） |
| Embedding / Rerank | OpenAI text-embedding、BGE、Jina；Cohere Rerank、bge-reranker |
| 记忆框架 | **Mem0**（写-更新-检索全流程）、**Letta/MemGPT**（OS 式分页记忆）、Zep（时序知识图谱）、LangGraph Checkpointer（状态持久化） |
| 会话缓存 | Redis（对话状态）、数据库 |
| 知识图谱 | Neo4j、GraphRAG |

### 5. 加分点

- **MemGPT 的启示**：把 LLM 当操作系统，上下文窗口是"主存"，外部存储是"磁盘"，满了自动换页——这是短期/长期记忆协同的经典范式。
- **Generative Agents（斯坦福小镇）**：检索用三因子打分——recency（新近度）+ importance（重要性）+ relevance（相关性），并有 reflection 机制定期生成高层记忆，至今仍是长期记忆设计的参考模板。
- **难点不在存，在写与更新**：冲突记忆如何裁决、记忆投毒（恶意内容写入长期记忆持久化生效）和隐私合规，比选型更值得讨论。
- **务实建议**：不是所有 Agent 都需要向量库——先问"要不要跨会话"；只需任务内记忆时，scratchpad + 文件 + 摘要往往就够了，架构复杂度应该跟着需求走。

## Q5: Tool Use 是扩展 Agent 能力的有效途径。请解释 LLM 是如何学会调用外部 API 或工具的？

### 1. 先纠正一个心智模型：模型不"执行"工具，只"生成"调用

LLM 的全部工作就是**按约定格式生成一段结构化文本**（工具名 + 参数），真正的执行在运行时层：

```
用户请求 → LLM 生成 {tool, args} → 运行时解析并执行 → 结果作为 Observation 回填 → LLM 继续推理
```

模型要学习的只有两件事：**何时调用**（决策）、**怎么填参数**（生成）。

### 2. 模型怎么"知道"工具存在：工具描述即接口

- 每个工具以 Schema 形式注册：`name + description + JSON Schema 参数说明`，注入 prompt 或通过 API 的 tools 字段传入。
- 模型基于**用户意图与工具描述的语义匹配**来选择工具——所以工具描述质量直接决定调用质量，写工具文档相当于给模型看 API 文档。
- 这也解释了为什么**换新工具不需要重新训练模型**：工具用法通过描述 zero-shot 注入，训练固化的是"读文档、填参数"这个通用能力。

### 3. 模型怎么"学会"调用：训练层

| 方法 | 做法 | 代表 |
|------|------|------|
| **SFT（监督微调）** | 构造"问题 → 正确调用格式"的标注对话，含多轮工具交互轨迹；数据来自人工标注、强模型蒸馏、真实 API 日志 | GPT-4 function calling、GLM 等 |
| **自监督挖掘** | 让模型自己在语料中插入 API 调用，只保留"填入结果能降低后续文本困惑度"的样本 | Toolformer (2023) |
| **RL / 可验证奖励** | 任务成败可验证（代码跑没跑通、任务完没完成），用结果信号优化调用策略 | RLVR 类后训练 |

### 4. 接口格式的演进

1. **ReAct 纯文本协议**：`Action: Search[query]`，靠正则解析——脆弱，格式错误即失败。
2. **Function Calling（2023 标准化）**：JSON Schema 定义工具，模型输出受约束的 JSON。
3. **受约束解码**：推理引擎在采样时直接屏蔽不合 schema 的 token，从生成层面保证格式合法（strict mode）。
4. **MCP（协议标准化）**：工具侧与模型侧解耦，工具实现一次、所有支持 MCP 的 Agent 都能用——类比"工具界的 USB"。

### 5. 运行时的可靠性保障（工程层）

训练让模型"会调"，工程让它"调得稳"：

- **Schema 校验**：Pydantic/zod 验证参数；校验失败把错误信息回填给模型自纠（错误即反馈信号）。
- **幻觉防御**：模型可能编造不存在的工具/参数 → 只允许从注册表选择 + 严格校验。
- **权限门控**：写操作、支付类敏感工具加人工确认。
- **超时/重试/幂等**：外部世界不可靠，调用层要兜底。

### 6. 加分点

- **Toolformer 的筛选标准很优雅**：不是"会调 API 的样本就保留"，而是"调了 API 之后模型对后续文本的预测变容易了才保留"——用困惑度增益自动判断哪些 API 值得学。
- **工具规模大了要 RAG**：工具几百个时全部塞进 prompt 不现实，先按任务检索相关工具再注入（tool retrieval），MCP 场景尤其如此。
- **CodeAct 趋势**：让模型生成代码来组合工具调用，比单次 function calling 表达力强（循环、变量、逻辑组合），执行引擎只需沙箱跑 Python。
- **一句话总结**：训练层教会模型"读文档填参数"的通用能力，描述层提供具体工具的 zero-shot 接口，工程层保证执行可靠——三层共同构成 Tool Use 体系。
