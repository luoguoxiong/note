# netc-pc-web-admin 路由权限方案设计

> 版本：v1.1（对齐实施落地代码）
> 适用项目：`netc-pc-web-admin`（Vue3 + TypeScript + Pinia + vue-router 4 + micro-app 微前端基座）
>
> **v1.1 变更（相对 v1.0 设计稿）**：
>
> - 拦截反馈由「403 页面」调整为「**当前页弹窗**（PermissionDialog）」：站内导航被拒留原页弹窗，首次导航落首页弹窗（对齐老项目体验）
> - 新增 **下单权限校验**（`meta.requireOrderPermission`，getOrderTips 两层校验）与 **authParam** 动态权限码
> - 守卫 ③ 步升级为「**按需阻塞 + 超时降级（3s）+ 后台预热**」，无权限标记路由零接口阻塞
> - 落地细节文档以《permission.md》为准，本文保留设计推导与老项目对照

## 一、背景与现状

### 1.1 项目现状

| 项       | 现状                                                                                                                                        | 位置                                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 路由注册 | 全量静态注册，无动态路由                                                                                                                    | `src/router/index.ts` → `admin.ts` → `internal/` + `iframe/` + `micro-app/` |
| 路由守卫 | **完全没有 beforeEach 守卫**，任何路由直接放行                                                                                              | `src/main.ts`（`createMicroMainApp` 创建后未挂守卫）                        |
| 菜单     | 后端接口 `web.lightApplication.getApplicationInfoListByArea` 按用户返回（**后端已做菜单级权限过滤**），localStorage 缓存秒显，失败降级 mock | `src/stores/lightapp.ts`                                                    |
| 登录态   | token 取自 URL query / sessionStorage                                                                                                       | `src/utils/auth.ts`                                                         |
| 用户信息 | Pinia `useUserStore`（getInfo + 实名认证）                                                                                                  | `src/stores/user.ts`                                                        |

### 1.2 问题

1. **手输 URL 可绕过菜单**：菜单虽由后端按权限返回，但路由全量静态注册且无守卫，未授权用户直接输入路由（如 `#/admin/components`）即可进入页面。
2. **iframe 页面与基座路由一一对应**（`src/router/iframe/tools.ts` 等把老 PC 端页面挂在基座路由下），同样无权限拦截。
3. **微前端子应用**（user/order，activeRule `/admin/user`、`/admin/order`）由基座路由驱动，无守卫时子应用入口不受控。
4. 无统一 403/无权限页面，无登录失效统一跳转。

### 1.3 参考与教训（来自老项目 netc-pc-web）

老项目采用「白/黑名单数组 + 硬编码 path→ 权限 ID 映射 + 守卫 if-else」，存在以下问题，本方案需规避：

- 权限映射硬编码在守卫函数内部，路由定义与权限判断分离两处，可读性差
- 白名单用 `path.startsWith` 前缀匹配，容易误伤（如 `/admin/user` 与 `/admin/user-detail`）
- 无 meta 声明式配置，新增受控页面必须改守卫代码
- 权限数据源多套并存（ID/Map/角色），收敛性差

## 二、设计目标与原则

1. **声明式**：权限配置挂在路由 `meta` 上，路由定义处即权限声明处，新增受控页面零改动守卫。
2. **单一数据源**：菜单权限 = 路由权限 = 权限码，统一以 `menuCode`（后端菜单接口返回）为基准，预留独立权限码接口扩展位。
3. **守卫集中**：唯一一个 `router/guard.ts` 负责全部拦截逻辑，分管道（pipe）组织，便于测试。
4. **精准匹配**：白名单/权限路由一律 name 或完整 path 精确匹配，禁用 `startsWith` 前缀误伤。
5. **不阻塞首屏**：权限数据复用 `lightapp.ts` 已有的「缓存秒显 + 接口更新」机制，守卫等待缓存的菜单数据，不额外增加串行请求。
6. **微前端兼容**：守卫在基座路由层生效，覆盖 internal / iframe / micro-app 三类路由。

## 三、整体架构

```
URL 变化
  ↓
router.beforeEach（src/router/guard.ts，唯一守卫入口，返回值式导航）
  ↓ 按顺序执行管道（resolveNavigation）
① 免登录白名单（精确 name/path 匹配，目前仅 notFound；或 meta.anonymous）→ 放行
② 登录校验：无 token → return false 中止（跳登录页逻辑为注释预留，暂未启用）
③ 按需阻塞 + 超时降级：仅 await 当前路由所需数据
   （需绑码/下单权限 → userStore.init；声明 auth → permissionStore.init），
   等待上限 3s（INIT_TIMEOUT），超时视为「数据不可用」降级；未依赖数据后台预热
③' 用户数据不可用（超时/失败）→ 放行 + 告警埋点（跳过 ④⑤ 防误拦）
④ 需绑码路由：未绑客户编码 → 拉绑码关系 → 未绑码弹窗（4 场景）
⑤ 下单权限路由：requireOrderPermission → getOrderTips 两层校验 → 拦截弹窗
⑥ 未声明权限（meta.auth / meta.authParam 均无）→ 登录即可访问，放行
⑦ 权限元数据不可用（isAuthDataReady === false）→ 放行 + 告警埋点（可用性优先）
⑧ 权限校验：hasAuth(auth) 不满足 → 当前页弹窗
   （站内导航 return false 留原页 / 首次导航落回 /admin/home）
  ↓
路由组件渲染（internal 原生组件 / iframe 容器 / micro-app 子应用）
  ↓
router.isReady() 首次导航补偿（初始导航早于守卫注册时兜底再校验一次，幂等）
router.afterEach：埋点 pageCode 预留
```

## 四、权限数据源设计

### 4.1 权限集合（Pinia）

在 `src/stores/` 新增 `permission.ts`：

```ts
import { defineStore } from 'pinia'
import { ref, computed, reactive } from 'vue'
import { useLightAppStore } from './lightapp'

export const usePermissionStore = defineStore('permission', () => {
  const lightAppStore = useLightAppStore()

  /** 全部已授权 menuCode（含子菜单，拍平）：直接派生自 lightapp 的 serverMenus（仅「缓存/接口成功」数据） */
  const menuCodes = computed(() => lightAppStore.serverMenuCodes)
  /** 预留：独立权限码接口（按钮/功能码），首期可空 */
  const authCodes = ref<Set<string>>(new Set())
  /** 权限元数据是否可用（接口失败且无缓存时为 false，守卫按「放行 + 告警埋点」降级） */
  const isAuthDataReady = computed(() => lightAppStore.isServerMenuReady)

  /** 拦截弹窗状态（dialog + openPermissionDialog/closePermissionDialog，PermissionDialog 组件消费） */
  /** 绑码关系数据 bindInfo（getAppUserRelationAuth，未绑码弹窗 4 场景数据源，loadBindInfo 拉取） */
  /** 下单权限数据 orderTips / orderBlockTip（getOrderTips + queryCustomerInfo，loadOrderTips 两层校验） */
  // …… 详见 src/stores/permission.ts 与《permission.md》六、七节

  const isInitialized = ref(false)
  let initPromise: Promise<void> | null = null

  async function init(): Promise<void> {
    if (isInitialized.value) return
    if (initPromise) return initPromise
    initPromise = (async () => {
      // 复用 lightapp 的缓存秒显 + 接口更新，不重复请求
      await lightAppStore.init()
      // 预留：此处可并行请求独立权限码接口，填充 authCodes
      isInitialized.value = true
    })()
    return initPromise
  }

  /** 是否有权限（支持单个或任一命中） */
  function hasAuth(auth: string | string[]): boolean {
    const arr = Array.isArray(auth) ? auth : [auth]
    return arr.some((code) => menuCodes.value.has(code) || authCodes.value.has(code))
  }

  return { menuCodes, authCodes, isInitialized, isAuthDataReady, /* dialog、bindInfo、orderTips… */ init, hasAuth }
})
```

要点：

- **menuCode 即权限**：后端 `queryAreaMenuList` 已按用户身份过滤，能出现在返回里的菜单即代表有权限。基座路由的 `meta.auth` 直接填后端配置的 menuCode（如 `M3002`）。
- **实现调整（相对初稿）**：menuCode 拍平收集不在 permission store 内遍历 `menusList`，而是消费 `lightapp.ts` 的 `serverMenuCodes` computed——单一数据源，fallback 兜底数据天然被隔离（见 6.2 节）。
- **失败降级**：菜单接口失败时 `lightapp.ts` 会用 mock `defaultData` 兜底 UI 展示，但**不写入 `serverMenus`**，权限判断不受污染。

### 4.2 meta 类型扩展

扩展 `src/router/types.ts`：

```ts
export type RouteMetaAuth = {
  /** 路由名称（已有惯例） */
  name?: string
  /** 埋点页面编码（已有惯例） */
  pageCode?: string
  /** ===== 以下为权限方案新增 ===== */
  /** 所需权限：menuCode 或权限码；数组=任一满足；不配置=登录即可访问 */
  auth?: string | string[]
  /** 从路由 param 取权限码（如 iframe-code 动态路由的 :code 即 menuCode） */
  authParam?: string
  /** 免登录路由（如 404、登录中转页） */
  anonymous?: boolean
  /** 需绑码（客户编码）才能访问 */
  requireCustomerCode?: boolean
  /** 需下单权限（getOrderTips 两层校验，无权限弹「立即申请/审核中」弹窗） */
  requireOrderPermission?: boolean
} & Record<string | number | symbol, unknown>

export type ExtendedRouteRecordRaw = {
  path?: string
  component?: RawRouteComponent | null | undefined
  children?: ExtendedRouteRecordRaw[]
  meta?: RouteMetaAuth
  redirect?: string
} & Record<string, unknown>

/** 让 vue-router 的 to.meta / from.meta 获得上述权限字段类型 */
declare module 'vue-router' {
  interface RouteMeta extends RouteMetaAuth {}
}
```

### 4.3 路由声明示例

```ts
// src/router/iframe/order.ts —— 寄件类路由：需绑码 + 下单权限（守卫管道 ④绑码 → ⑤下单权限）
{
  name: 'order-config-single',
  path: '/admin/order-config-single',
  iframeComponent: defineAsyncComponent(() => import('@/views-iframe/order/single-order.vue')),
  meta: { requireCustomerCode: true, requireOrderPermission: true },
}

// src/router/iframe/code.ts —— 动态 iframe 路由：:code 即 menuCode，从 param 取权限码
{
  name: 'iframe-code',
  path: '/admin/iframe/:code',
  meta: { authParam: 'code' }, // 菜单存在即有权限，防 URL 手输绕过
}

// src/router/internal/index.ts —— 静态权限码（权限拦截测试路由，M9999 不存在于任何菜单配置）
{
  name: 'permissionDeny',
  path: '/admin/permission-deny',
  meta: { auth: 'M9999' },
}
```

**存量路由迁移策略**：现有路由默认不配置 `auth`（= 登录即可访问），按敏感度分批补充，避免一次性上线风险。当前已接入权限标记的路由：寄件相关（order/vts/global 等 iframe 路由，`requireCustomerCode` + `requireOrderPermission`）、动态 iframe 路由（`authParam`）、内置权限验证路由三个（`/admin/permission-deny`、`/admin/permission-bindcode`、`/admin/order-permission-test`）。

```ts
}

/** 守卫管道：返回 true 放行 / false 中止（留原页）/ 重定向目标（string path） */
async function resolveNavigation(to: GuardTarget, from?: GuardTarget) {
  // ① 免登录路由直接放行（WHITE_LIST 精确匹配，或 meta.anonymous）
  // ② 登录校验：无 token → return false（跳登录页逻辑为注释预留，暂未启用）
  // ③ 按需阻塞：只 await 当前路由所需数据（withTimeout 3s），未依赖数据后台预热

  // ④⑤ 业务权限校验（绑码 + 下单）→ 弹窗 + return false（站内）/ FALLBACK_PATH（首次导航）
  // ⑥ 未声明权限 → 放行
  // ⑦⑧ menuCode 权限校验 → 弹窗 + return false / FALLBACK_PATH
}

export function setupRouterGuard(router: Router) {
  router.beforeEach(async (to, from) => resolveNavigation(to, from))
  router.afterEach(() => {
    // 预留：页面 PV 埋点（meta.pageCode）；弹窗曝光埋点在 PermissionDialog onOpen 上报
  })

  // 首次导航补偿：初始导航早于守卫注册时（createMicroMainApp 内部已 app.use(router)），
  // isReady 后对当前路由再校验一次（幂等）
  router.isReady().then(() => {
    const current = router.currentRoute.value
    resolveNavigation(current).then((result) => {
      if (result === true || result === false) return
      router.replace(result)
    })
  })
}
```

### 5.2 挂载守卫

`src/main.ts` 在 `createMicroMainApp` 之后：

```ts
import { setupRouterGuard } from './router/guard'

export const { app, router } = createMicroMainApp(App as Any, {
  /* 现有配置 */
})

setupRouterGuard(router)
```

> 说明：`createMicroMainApp` 返回标准 vue-router 实例，`beforeEach` 用 vue-router 4 的返回值式导航（`return true / return false / return route`），不再使用 `next()` 回调。
> 另外 `main.ts` 末尾有**启动预热**：有 token 时不等守卫/页面挂载，直接发起 `userStore.init()` 与 `lightAppStore.init()`，与 JS chunk 加载并行（store 单例与缓存保护，守卫复用同一请求结果，不重复请求）。

### 5.3 拦截反馈（v1.0 为 403 页面，落地调整为当前页弹窗）

**v1.0 设计**为新增 `src/views/forbidden/index.vue`（`/403`）页面 + `query.reason` 区分文案。**落地实施时调整**为对齐老项目体验的「当前页弹窗」方案（v1.1）：

- 新增全局唯一弹窗组件 `src/components/permission-dialog/index.vue`，在 `App.vue` 根组件挂载；
- 由路由守卫经 `permissionStore.openPermissionDialog(type, target)` 触发，三场景（`PermissionDialogType`）：`auth` 无访问权限 / `customerCode` 未绑码（4 场景，文案后端直出）/ `order` 无下单权限（立即申请/审核中）；
- 站内导航被拒：`return false` 留在原页 + 弹窗；首次导航（直接 URL 进入）：无原页可停留，落回首页 `/admin/home` + 弹窗；
- 详见《permission.md》六、七节。

## 六、与现有体系的联动及特殊处理

### 6.1 菜单联动（无需改动）

`stores/lightapp.ts` 的菜单已由后端按权限返回，**菜单显隐天然是权限过滤后的结果**，路由守卫只是防绕过的兜底。二者数据同源（menuCode），不会出现「菜单显示但路由拦截」或反之的分裂。

### 6.2 菜单接口失败降级的处理（关键）

现状：`lightapp.ts` 在接口失败时调用 `applyFallbackMenu()` 用 mock `defaultData` 兜底展示。若权限判断直接读 `menusList`，会导致**接口失败时用户凭 mock 菜单获得越权访问**。

处理方式：

- `permission.ts` 的 `collect` 改为只从**接口成功的数据**收集，做法是在 `lightapp.ts` 增加一个仅接口成功才更新的 `serverMenuCodes`（computed 拍平 menuCode），permission store 只消费它；`applyFallbackMenu` 分支不更新该字段。
- 守卫在权限元数据**不可用**（接口失败且无缓存）时的策略：**放行 + 告警埋点**（保证可用性优先），或「按产品要求降级到全拦截」。本方案默认放行，理由：菜单都打不开的异常网络场景下，阻断用户访问所有页面的代价更高；同时后端接口本身仍有鉴权兜底。

### 6.3 iframe 路由

`src/router/iframe/` 下路由承载老 PC 页面，**老页面内部已有一套自己的权限**（老项目守卫与按钮权限）。基座层只需：

- `meta.auth` 配置与老项目一致的 menuCode，防绕过；
- 不在 iframe 容器内部重复做按钮级权限，保持单一职责。

### 6.4 微前端子应用路由

现状：`main.ts` 的 `microApps` 配置（user/order，`parentRouteName: 'Admin'`）为**注释预留**状态；当前微前端路由经 `src/router/micro-app/index.ts` 的 `meta.microApp.url` 挂载（如 `/admin/order`）。守卫覆盖原则不变：

- 在基座侧为对应路由（如 `/admin/order`）配置 `meta.auth` / 业务权限标记，守卫在进入子应用**之前**拦截；
- 子应用内部页面的细粒度权限由子应用自行实现（本方案范围外，但约定子应用可复用基座通过 `window.__POWERED_BY_MICRO_APP__` / data 传递的权限集合，避免重复拉取）。

### 6.5 redirect 兼容

登录回跳：老 PC 登录页拿到 `redirect` 参数后，拼回 `https://<admin-host>/<version>/#/...`，token 走 URL query（`auth.ts` 的 `getTokens` 已支持）。

## 八、测试要点

1. **未登录**：直接访问任意受控路由 → 当前 `return false` 中止（跳登录页逻辑为注释预留，启用后应携带 redirect 并支持登录后回跳）
2. **无权限**：手输 URL 访问已配置 `meta.auth` 但用户无该 menuCode 的路由 → 弹「无访问权限」弹窗，首次导航落回首页 `/admin/home`；站内导航被拒留在原页
3. **有权限**：菜单点击与手输 URL 均正常进入
4. **白名单**：404（`notFound`）及 `meta.anonymous` 路由未登录可直接访问
5. **菜单接口失败**（可断网/mock 500）：有 localStorage 缓存 → 权限按缓存判断；无缓存 → 放行并上报 `other_router_guard_auth_unavailable_v1` 埋点
6. **接口超时**：用户/权限接口挂起超过 3s（INIT_TIMEOUT）→ 降级放行 + 埋点（reason=userDataTimeout），不误拦绑码/下单路由
7. **微前端**：`/admin/order` 等子应用路由无权限时被基座守卫拦截，子应用不加载
8. **刷新页面**：hash 路由 + token 在 sessionStorage，刷新后守卫不重复请求（Pinia 单例 + lightapp 缓存生效）
9. **路由并发**：快速连续切换路由时守卫的 init 单例不被重复触发（`initPromise` 保护）
10. **内置验证路由**：`/admin/permission-deny`（必拦截弹窗）、`/admin/permission-bindcode`（未绑码弹窗 4 场景）、`/admin/order-permission-test`（下单权限弹窗）

| 场景               | 按钮组合              | 确认动作                           | 取消动作                             |

| 老客-未匹配商务    | 去绑码 / 申请专属商务 | 跳绑码页                           | 跳 `/admin/user/customer-code-apply` |
