# MySQL 八股文

## Q1: 讲一下 MySQL 的逻辑架构。一条 SQL 语句在 MySQL 中是如何执行的？

### 两层架构

| 层 | 组件 | 职责 |
|----|------|------|
| **Server 层** | 连接器、查询缓存（8.0 已移除）、分析器、优化器、执行器、内置函数 | 跨引擎的功能：权限判断、SQL 解析与优化 |
| **存储引擎层** | InnoDB、MyISAM、Memory 等 | 数据真正存取，插件式可替换（默认 InnoDB） |

### 一条查询语句的执行流程（select）

1. **连接器**：建立 TCP 连接 → 校验用户名密码 → 查权限并存入会话（之后改权限不影响已建连接；`wait_timeout` 默认 8h，长连接建议用连接池，且定期 disconnect 或 `mysql_reset_connection` 防内存涨）。
2. **查询缓存**：以 SQL 为 key 缓存结果。**任何对表的更新都会清掉该表全部缓存**，命中率极低，8.0 直接移除。
3. **分析器**：词法分析（识别出关键字、表名、列名）→ 语法分析（生成 AST，报 `You have an error in your SQL syntax`）。
4. **优化器**：选择索引、决定 join 表顺序等，生成执行计划。
5. **执行器**：先校验对该表有无执行权限 → 按计划调用存储引擎接口逐行取数据 → 返回结果。

### 一条更新语句多了什么（update）

前 5 步相同，额外涉及 **undo log、redo log、binlog**：

```
1. 执行器调用引擎接口读出该行（若在 Buffer Pool 有则直接返回）
2. 引擎把旧值写入 undo log
3. 在 Buffer Pool 中更新数据页（该页变"脏页"），同时记录 redo log，状态 prepare
4. 写 binlog
5. 提交事务，redo log 状态改为 commit（两阶段提交）
```

### 关键理解（加分点）

- **更新语句与 Buffer Pool**：数据更新先改内存页，不直接刷盘；靠 WAL（Write-Ahead Logging，redo log）保证崩溃后能恢复，把随机写磁盘转化为顺序写，这是 MySQL 高性能写的关键。
- **权限在连接器一次读取**：所以改了权限要"重连"才生效。

## Q2: 为什么 MySQL 索引用 B+ 树？而不是 B 树、哈希表、红黑树、跳表？

### 各方案对比

| 结构 | 缺陷 | B+ 树优势 |
|------|------|-----------|
| 哈希表 | 只支持等值查询，不支持范围和排序 | B+ 树叶子节点有序且是双向链表，天然支持范围/排序 |
| 红黑树/二叉树 | 树太高，磁盘 IO 次数 = 树高 | 单节点 16KB 放多个 key，树矮胖（千万数据约 3~4 层），3 次左右 IO 搞定 |
| B 树 | 数据与索引混存，非叶子节点也放数据 → 单页放的 key 少、树更高；范围查询需中序回溯 | 非叶子只存索引，叶子才存数据，扇出更大；叶子链表直接顺序扫 |
| 跳表 | 用于内存结构（如 Redis ZSet），磁盘上空间局部性差 | — |

### 数量级估算（加分点）

- 假设主键 bigint 8B + 指针 6B ≈ 14B，16KB 页的非叶子节点可放约 **1200 个 key**。
- 3 层 B+ 树 ≈ 1200 × 1200 × 16（叶子每页放 16 行）≈ **2300 万行**，即千万级表最多 3 次 IO。
- InnoDB 读数据最小单位是页（16KB），磁盘预读友好——B+ 树一个节点就是一页，正好对齐。

## Q3: 聚簇索引和二级索引是什么？什么是回表、覆盖索引、索引下推？

### 两类索引

| 类型 | 结构 | 示例 |
|------|------|------|
| **聚簇索引（主键索引）** | 叶子节点存**整行数据** | 主键 id |
| **二级索引（辅助索引）** | 叶子节点存**索引列 + 主键值** | 普通 `name` 索引：叶子为 (name, id) |

- 每张表**必须有且只有一个聚簇索引**：有主键用主键；无主键用第一个非空唯一索引；都没有则生成隐藏的 6 字节 `row_id`。
- 二级索引查到主键后，再回聚簇索引查整行，就是 **回表**。

### 优化手段

| 手段 | 做法 | 例子 |
|------|------|------|
| **覆盖索引** | 查询列都在索引里，免回表 | `select id,name from t where name='a'`（name 索引即覆盖）；高频查询可建联合索引 (name, phone) 覆盖"查 phone" |
| **索引下推（ICP，5.6+）** | 联合索引中，即使某列不能走索引定位，也可在**引擎层先过滤**再回表，减少回表次数 | 联合索引 (name, age)，`where name like '张%' and age=10`：老版本按 name 查出所有张姓全部回表；ICP 在叶子层先过滤 age=10 |
| **联合索引** | 一个索引多列，注意最左前缀与列顺序（区分度高的、等值条件的在前） | — |

### 关键理解（加分点）

- 主键尽量**自增**：顺序插入只追加写，无页分裂；随机主键（如 UUID）会导致频繁页分裂、页碎片，且二级索引叶子更大。
- 判断一条 SQL 是否"索引白建"：看执行计划 Extra 里是否 `Using index`（覆盖索引）、`Using index condition`（索引下推）。

## Q4: 最左前缀原则是什么？哪些场景索引会失效？

### 最左前缀原则

联合索引 (a, b, c) 相当于建了 (a)、(a,b)、(a,b,c) 三个索引：

- 必须**从最左列开始且连续**命中：`a=1 and b=2 and c=3` 全命中；`b=2`、`a=1 and c=3` 只命中 a；`b=2 and c=3` 全不命中。
- 遇到范围查询（>、<、between、like 前缀）**后面的列停止使用索引**（但 8.0 的 ICP 仍可用来过滤）：`(a>1 and b=2)` 中 b 用不上索引定位，仅可下推过滤。
- 优化器会调整等值条件顺序：`where b=2 and a=1` 等价于 `a=1 and b=2`，不影响命中。

### 常见索引失效场景

| 场景 | 原因/示例 |
|------|-----------|
| 对索引列做函数或运算 | `where id+1=10`、`where year(create_time)=2024` → 等价于改了索引结构 |
| 隐式类型转换 | `where phone = 13800000000`（phone 是 varchar，比较时字符串转数字，等价于对列做 cast） |
| 隐式字符集转换 | join 两表字符集不同时，关联列被转码，等价于加函数 |
| 模糊匹配左边带 % | `where name like '%ab'`；`'ab%'` 可以走索引（前缀匹配） |
| or 两侧有非索引列 | 需全表扫；or 两侧都有索引时可走 index merge |
| 不满足最左前缀 | 跳过左列 |
| 优化器判定全表更快 | 回表成本高（select * + 大量数据）时可能放弃索引；`is not null`、`!=`、`not in` 大多数情况不走 |

### 关键理解（加分点）

- "失效"多数不是规则一刀切，而是**优化器基于成本（io_cost + cpu_cost）估算后决定**，可用 `force index` 干预排查，但根治靠改写 SQL / 调整索引 / 统计信息。
- 隐式类型转换记一个方向：**字符串列 = 数字**（列被转，失效）；**数字列 = 字符串**（常量被转，不失效）。

## Q5: 索引怎么设计？什么时候该建、什么时候不该建？

### 建索引的原则

1. **唯一性强的列优先**（区分度 = count(distinct col) / count(*)，接近 1 才好）。
2. **长字符串用前缀索引**：`alter table t add index (email(12))`，注意前缀索引**不能覆盖索引、不能用于 order by/group by**。
3. **联合索引替代多个单列索引**，控制索引数量（每个索引都是一棵 B+ 树，占空间、拖慢写入，主从复制也变慢）。
4. 查询频率高、条件/排序中出现的列建索引；能顺便形成**覆盖索引**的联合索引优先。
5. 用 `explain` 验证实际生效情况，而不是想当然。

### 不建议建索引

- 频繁**更新**的列（维护索引代价大）。
- 区分度低的列（如性别）。
- 表数据量很小（全表扫更快）。
- where / order by / group by 用不到的列。

### 关键理解（加分点）

- order by 想走索引：联合索引的排序方向需与 order by 一致（8.0 支持降序索引），where 与 order by 列最好同属一个联合索引，避免 filesort。
- 索引不是越多越好：写放大（每次增删改要维护所有相关索引）+ 空间 + 优化器选择成本。

## Q6: 事务的 ACID 分别靠什么实现？

| 特性 | 含义 | 实现机制（InnoDB） |
|------|------|--------------------|
| **原子性** | 全做或全不做 | **undo log**：记录反向操作，回滚时逆序执行 |
| **持久性** | 提交后永久保存 | **redo log**：WAL，先顺序写日志再异步刷数据页，崩溃恢复时重放 |
| **隔离性** | 并发事务互不干扰 | **MVCC**（读写不阻塞）+ **锁**（写写冲突） |
| **一致性** | 数据从一个合法状态到另一个合法状态 | 以上三者 + 应用层约束（主外键、业务逻辑）共同保证 |

### 关键理解（加分点）

- AID 是手段，**C 是最终目的**；undo/redo 都采用"先写日志、后写数据"（日志先行）的思路，把随机写变顺序写。
- redo log 是**物理日志**（某页某偏移改成了什么），undo log 是**逻辑日志**（反向 SQL / 旧版本行，还服务 MVCC 读旧版本）。

## Q7: 事务并发会产生哪些问题？四种隔离级别分别解决什么？

### 三大并发问题

| 问题 | 描述 |
|------|------|
| **脏读** | 读到别的事务**未提交**的数据，对方回滚则数据作废 |
| **不可重复读** | 同一事务内两次读**同一行**结果不同（别人 update 并提交） |
| **幻读** | 同一事务内两次**范围查询**行数不同（别人 insert/delete 并提交） |

### 隔离级别（由低到高）

| 级别 | 脏读 | 不可重复读 | 幻读 |
|------|------|------------|------|
| 读未提交 RU | 有 | 有 | 有 |
| 读已提交 RC | 无 | 有 | 有 |
| 可重复读 RR（**InnoDB 默认**） | 无 | 无 | 基本无（MVCC + 临键锁） |
| 串行化 | 无 | 无 | 无 |

- RU：直接读最新数据（不加锁不建快照）。
- RC：每次 select 都生成新的 ReadView。
- RR：事务内**第一次** select 生成 ReadView，之后复用 → 可重复读。
- 串行化：读加共享锁、写加排他锁。

### 关键理解（加分点）

- Oracle/PG 默认 RC，MySQL 默认 RR 的历史原因：早期 statement 格式 binlog 在 RC 下主从数据可能不一致（RR + statement 才安全）；现在 binlog 默认 row 格式，RC 也能保证复制安全，互联网公司大量用 RC（锁更少、并发更好）。
- RR 下的"可重复读"只针对快照读；幻读问题见 Q9。

## Q8: MVCC 的实现原理？ReadView 里有什么？

### 组成部分

1. **隐藏字段**（每行）：
   - `trx_id`：最近一次修改该行的事务 ID；
   - `roll_pointer`：指向 undo log 里的旧版本，多个版本串成**版本链**。
2. **undo log 版本链**：每次更新把旧版本写入 undo log，通过 roll_pointer 串联，能找到任意历史版本。
3. **ReadView**（读视图）：当前系统里"活跃（未提交）事务"的快照，字段：
   - `m_ids`：生成时刻活跃事务 ID 列表；
   - `min_trx_id`：m_ids 最小值；
   - `max_trx_id`：系统将分配的下一个事务 ID；
   - `creator_trx_id`：创建该 ReadView 的事务 ID。

### 可见性判断（对版本链上的每个版本取 trx_id 判断）

```
trx_id == creator_trx_id            → 自己改的，可见
trx_id <  min_trx_id                → 生成快照前已提交，可见
trx_id >= max_trx_id                → 快照后开启的事务，不可见
min_trx_id <= trx_id < max_trx_id:
    在 m_ids 中 → 未提交，不可见
    不在 m_ids 中 → 已提交，可见
不可见则沿 roll_pointer 找上一个版本，重试判断
```

### RC 与 RR 的区别（一句话考点）

- **RC**：每次 select 都新建 ReadView（能看到别人新提交的数据 → 不可重复读）。
- **RR**：只在事务第一次 select 时建 ReadView 并一直复用（可重复读）。

### 关键理解（加分点）

- MVCC 让**读写不阻塞**：写加锁，读走快照，不用为读上锁，这是 InnoDB 并发高的核心。
- 版本链清理依赖 purge 线程；长事务会拖住大量旧版本不被清理（undo 膨胀），**避免长事务**。

## Q9: 什么是幻读？InnoDB 怎么解决幻读？为什么说没完全解决？

### 幻读的专门定义

指**当前读**下两次范围查询行数不同：事务 A 两次 `select ... for update` 之间，事务 B 插入了一行并提交，A 第二次读到多出的行。

- 普通快照读靠 MVCC 的 ReadView 复用已能保证"看不到"新插入行，不算幻读问题。

### InnoDB 的解法

| 读方式 | 防幻读手段 |
|--------|-----------|
| 快照读（普通 select） | MVCC（RR 复用同一 ReadView） |
| 当前读（select ... for update / lock in share mode、update、delete） | **Next-Key Lock = 记录锁 + 间隙锁**，锁住记录及记录间空隙，阻止其他事务插入 |

### 为什么"没完全解决"

同一事务内**快照读和当前读混用**的场景：

```
T1: select * from t where id>0;        -- 快照读，看到 N 行
T2: insert into t ... ; commit;        -- 插入新行
T1: update t set ... where id>0;       -- 当前读，新行被更新且 trx_id 变成 T1
T1: select * from t where id>0;        -- 快照读：新行是自己改的 → 可见，幻读出现
```

（原理：自己更新过的行 trx_id 变成自己的，重新走可见性判断就可见了。）

### 关键理解（加分点）

- 要彻底防幻读：事务一开始就用当前读（`for update`）把范围锁住，全程只用当前读。
- 间隙锁只在 RR 隔离级别存在；这也是 RC 并发更高、互联网场景多选 RC 的原因之一（无间隙锁，锁冲突少）。

## Q10: MySQL 有哪些锁？行锁的三种算法是什么？

### 按粒度

| 锁 | 粒度 | 场景 |
|----|------|------|
| 全局锁 | `flush tables with read lock`，库只读 | 逻辑备份（MyISAM 时代）；InnoDB 可用 `--single-transaction`（利用 MVCC）免锁备份 |
| 表级锁 | 表锁、元数据锁 MDL、**意向锁**、AUTO-INC 锁 | MDL 防止 DDL 与 DML 并发冲突（增删改查自动加 MDL 读锁、DDL 加写锁，事务不提交会堵住后续 DDL）；意向锁标记"表内行被锁了"，使表锁判断无需逐行检查 |
| 行级锁 | InnoDB 独有，锁在索引记录上 | 高并发主力 |

### 行锁三种算法

| 算法 | 锁定范围 | 触发 |
|------|----------|------|
| **Record Lock** | 单条索引记录 | 等值命中唯一索引 |
| **Gap Lock** | 两条记录之间的开区间，只防插入不互斥 | 防幻读 |
| **Next-Key Lock** | Record + Gap，前开后闭区间 `(a, b]` | RR 下的默认算法 |

### 关键理解（加分点）

- **行锁锁的是索引**：走什么索引锁什么范围；没有索引/不走索引 → 升级为锁全表所有记录（等价表锁效果）。
- 加锁规则（RR，5.x）：默认 next-key；等值查唯一索引命中退化为记录锁；等值查非唯一索引，会锁到第一个不满足条件的值（右侧间隙）。
- 插入意向锁：插入前在 gap 上设置的特殊意向锁，多个事务插不同位置不冲突。

## Q11: update 语句没走索引，为什么可能锁全表？

- 行锁加在**索引记录**上；`where` 条件不走索引时，InnoDB 只能全表扫描，**扫描过程中把所有扫过的行都加上锁**（RR 下还加 next-key），事务提交才释放 → 效果等于锁全表，其他事务的增删改全部阻塞。
- 排查与规避：
  - `explain` 确认 update/delete 走索引；
  - 没有可用索引就先加；
  - 控制事务大小、尽快提交；
  - RC 隔离级别下没有间隙锁，非命中行会被"半一致性读"释放，影响面小一些。

## Q12: 死锁是什么？怎么排查、怎么避免？

### 产生条件

互相持有并等待对方的锁。典型：

```
T1: 锁 id=1 → 想锁 id=2
T2: 锁 id=2 → 想锁 id=1
```

或间隙锁互相不冲突（gap lock 之间兼容）却都阻塞对方 insert → 死锁。

### InnoDB 的处理

- 死锁检测（默认开启 `innodb_deadlock_detect`）：发现回环等待，回滚**代价小**的事务；高并发热点行更新时检测本身有 O(n²) 开销，可临时关闭靠 `innodb_lock_wait_timeout` 兜底。
- 相关参数：`show engine innodb status` 查看最近死锁日志；`information_schema.innodb_trx / data_locks / data_lock_waits`（8.0）。

### 避免手段

1. 事务内**按相同顺序**访问资源（如都按 id 升序）。
2. 小事务快提交，避免长事务跨多条语句持锁。
3. 一次性锁够需要的记录（先 `for update` 锁住再做逻辑），避免"锁了又解锁再加锁"的竞态。
4. 热点行更新：拆行、排队机制（如 Redis 分布式锁）、降低并发。

## Q13: redo log、undo log、binlog 的区别？两阶段提交是怎么回事？

### 三大日志

| 日志 | 层 | 类型 | 作用 | 写入方式 |
|------|----|------|------|----------|
| **redo log** | InnoDB | 物理日志 | 崩溃恢复（保证持久性），循环写固定大小 | 随事务提交顺序写 |
| **undo log** | InnoDB | 逻辑日志 | 回滚 + MVCC 读旧版本 | 随数据修改写入 |
| **binlog** | Server 层 | 逻辑日志（statement/row/mixed） | 主从复制 + 归档/恢复，追加写 | 事务提交时写 |

### 两阶段提交（redo log prepare → binlog → redo log commit）

为了让两份日志（引擎层 redo、Server 层 binlog）**逻辑一致**，防止崩溃恢复后主从/库间不一致：

```
1. redo log 写入，状态 prepare
2. binlog 写入
3. redo log 状态 commit
```

崩溃恢复规则：redo log 已 prepare 但未 commit 时，看 binlog 是否完整——完整则提交，不完整则回滚。（binlog 是否完整的校验：statement/row 格式末尾有完整性标记。）

反证：先写 redo 后写 binlog，宕机则主库有这条更新、从库没有；反之主库丢了更新而从库有。

### 刷盘时机（性能关键参数）

| 参数 | 值 | 行为 |
|------|----|------|
| `innodb_flush_log_at_trx_commit` | 1（默认） | 每次提交都 fsync，最安全 |
| | 0 | 每秒刷一次，宕机丢 1s 事务 |
| | 2 | 提交时写到 OS page cache，MySQL 崩不丢、机器崩丢 1s |
| `sync_binlog` | 1（默认） | 每次提交 fsync binlog |
| | 0 | 交给 OS 刷 |
| | N | 攒 N 个事务刷一次 |

- 双 1（两个参数都为 1）= 不丢数据；金融业务建议双 1，吞吐场景可放宽。
- **组提交**：多个事务的刷盘合并成一次 fsync，配合 redo log 双 1 也能有不错吞吐；binlog 同理。

### 关键理解（加分点）

- redo log 循环写（write pos 追 checkpoint），写满会阻塞业务触发"刷脏页"；binlog 追加写，写满切换下一个文件。
- binlog 三格式：statement 记 SQL（日志小但可能主从不一致，如 now()/uuid()）、row 记行变更（默认，大而安全，可解析做数据订阅如 canal）、mixed 自动切换。

## Q14: 讲讲 Buffer Pool。脏页是什么？change buffer 干什么用？

### Buffer Pool

- InnoDB 以**页**（16KB）为单位在内存里缓存数据页/索引页，读写都先走 Buffer Pool，缓解磁盘随机 IO。
- 用**改良 LRU**管理：链表分 young（5/8）和 old（3/8）区；新页先入 old 区头部，在 old 区停留超过 1s 再次被访问才移到 young 区——防止一次全表扫描/预读把热点数据冲出去。
- 后台线程异步把**脏页**（被修改、与磁盘不一致的页）刷盘；触发时机：redo log 快写满（`innodb_max_dirty_pages_pct`）、内存不足淘汰、正常关闭、空闲。

### change buffer

- 对**二级索引**的写操作，若目标页不在 Buffer Pool，先把变更缓存在 change buffer，**避免读盘**；后续该页被读到时再合并（merge），后台也会定期 merge。
- 仅对普通二级索引生效（唯一索引必须读页校验唯一性，用不上）；写多读少场景收益大（如日志、账单表）。

### 关键理解（加分点）

- 生产常见性能抖动原因之一：脏页刷盘引发的 IO 风暴；可通过控制 redo log 大小、脏页比例提前平滑刷盘。
- 查看命中率：`show engine innodb status` 的 Buffer pool hit rate（正常应 > 99%）。

## Q15: 主从复制的原理？延迟怎么产生的、怎么解决？

### 复制流程

```
主库：事务提交 → 写 binlog → dump 线程推送
从库：IO 线程接收 → 写 relay log（中继日志）
      SQL 线程读 relay log → 重放（5.7 可并行复制，8.0 writeset）
```

### 主从延迟原因

- 从库单 SQL 线程重放（老版本），主库多线程写入；
- 大事务、大表 DDL 在从库重放慢；
- 从库机器差、锁竞争、单表数据过大。

### 影响：读写分离下读到旧数据。解决

1. 强制走主库：对一致性敏感的读（如写后立刻读）路由主库。
2. sleep / GTID 等待：读从库前先 `select master_pos_wait(file, pos, timeout)` 或 8.0 的 `wait_for_executed_gtid_set`，等到位点再读。
3. 判断位点：读库记录每次写的主库 binlog 位点，读请求对比从库位点，没追上就路由主库或等待。
4. 优化复制：row + 并行复制（`slave_parallel_workers`、writeset）、升级硬件、拆大事务。

### 主从切换与高可用

- **可靠性优先**：判断 seconds_behind_master=0 后，把从库只读 → 等主库流量落地 → 切换（可能短暂不可写）。
- **可用性优先**：直接切，可能造成数据不一致（binlog 缺失/冲突），需配合 GTID 与校验。

### 关键理解（加分点）

- binlog 位点 + GTID（全局事务 ID）是复制与故障切换的基石；MHA/Orchestrator 等工具基于此做自动切换。
- 半同步复制（semi-sync）：至少一个从库确认收到 binlog 才返回客户端成功，在性能与安全间折中。

## Q16: explain 怎么看？哪些字段最关键？

### 关键字段

| 字段 | 关注点 |
|------|--------|
| `type` | 访问类型，从好到差：`system > const > eq_ref > ref > range > index > ALL`；生产 SQL 至少要到 range，杜绝 ALL（大表） |
| `key` / `key_len` | 实际用的索引；key_len 可推断联合索引用了几列（长度 = 类型字节数 + 长度标记，varchar 额外 2B，可为 NULL 额外 1B） |
| `rows` | 预估扫描行数（估算值，非精确） |
| `Extra` | 关键信息 |
| `filtered` | 按条件过滤后剩余比例的估算 |

### Extra 常见值

| 值 | 含义 | 好坏 |
|----|------|------|
| `Using index` | 覆盖索引，不回表 | 好 |
| `Using index condition` | 索引下推 | 好 |
| `Using where` | server 层过滤 | 一般 |
| `Using temporary` | 用了临时表（group by/distinct 无索引可用） | 差 |
| `Using filesort` | 额外排序，没利用索引顺序 | 差 |
| `Using join buffer` | join 没走索引，用 BNL 块嵌套循环 | 差 |

### 关键理解（加分点）

- `rows * filtered` 估算驱动表选择；join 时小表驱动大表（`straight_join` 可干预）。
- 8.0 可用 `explain analyze` 看真实执行时间与各算子实际行数，比估算靠谱得多。

## Q17: 线上 SQL 慢了，你怎么排查和优化？

### 定位

1. `show processlist` 看当前执行中的查询（是否锁等待、长时间执行）。
2. 慢查询日志：`slow_query_log=on`，`long_query_time` 阈值，配合 `pt-query-digest` / mysqldumpslow 聚合分析，找出高频/高耗时 SQL。
3. 监控：performance_schema / sys 库（8.0）、云数据库的慢 SQL 面板。

### 分析与优化（自上而下）

| 层次 | 手段 |
|------|------|
| SQL 层 | explain 分析：加/改索引（覆盖、联合、最左前缀）、改写 SQL（深分页、join 改写、减少 select *）、避免索引失效写法 |
| 结构层 | 冷热分离、大表拆分（垂直/水平）、冗余字段/反范式减少 join |
| 参数层 | 调整 buffer pool 大小、双 1 与否、连接池参数 |
| 架构层 | 读写分离、缓存（Redis）、异步化、分库分表 |

### 关键理解（加分点）

- 先看是不是**偶发抖动**（脏页刷盘、锁等待、统计信息过期触发错误计划，`analyze table` 更新统计信息）还是**持续慢**，处理路径完全不同。
- 慢 SQL 治理优先做"高频 + 高耗时 + 影响大"的头部 SQL，别平均用力。

## Q18: limit 1000000,10 深分页为什么慢？怎么优化？

### 为什么慢

- `limit N, M`：先取出前 N+M 行，再**丢弃 N 行**，返回 M 行；offset 越大浪费越多。
- 若还带 order by 无索引，加上 filesort 更糟。

### 优化方案

1. **子查询定位起始主键（延迟关联）**：

```sql
select * from t
where id >= (select id from t where cond order by id limit 1000000, 1)
order by id limit 10;
-- 或 join 写法：先用覆盖索引只扫 (cond,id) 小索引拿主键，再回表 10 行
```

2. **游标/滚动分页**（推荐）：记住上一页最后一条的排序键，下一页 `where id > last_id order by id limit 10`——每页恒定开销，但不能跳页（移动端瀑布流场景天然适配）。
3. 业务侧限制最大页码（ES、B 站等都这么干）。

### 关键理解（加分点）

- 优化本质：把"扫描 N+M 行回表"变成"覆盖索引扫到起点 + 回表 M 行"，或彻底不扫前面页。

## Q19: count(*)、count(1)、count(主键)、count(字段) 的区别？为什么 InnoDB 没有存总数？

### 区别

| 写法 | 行为 |
|------|------|
| `count(*)` | 官方优化过，不取值直接按行累加，**建议写法** |
| `count(1)` | 同 count(*)，无差别 |
| `count(主键)` | 拿主键值判断非空累加（InnoDB 会选最小的索引树遍历） |
| `count(字段)` | 要把字段取出判断非 NULL 才计数（可为 NULL 的字段会少算），且需取值，最慢 |

（MyISAM 存了总行数，无 where 的 count(*) 直接返回；InnoDB 因 MVCC 多版本并发下"总行数"因事务而异，没法存一个统一值。）

### 为什么不存总数 / count 怎么优化

- MVCC 下不同事务看到的行数不同，任何存的总数都可能"错"，InnoDB 选择现算。
- 大表 count 优化：另建计数表（事务内同步增减）、Redis 计数（容忍误差 + 定期校准）、show table status 的近似值（不精确）、ES/数仓侧统计。

## Q20: char 和 varchar 的区别？varchar(50) 的 50 是什么意思？null 相关怎么考虑？

| 对比点 | char | varchar |
|--------|------|---------|
| 长度 | 定长，不足补空格 | 变长 |
| 存储 | 固定字节数 | 实际内容 + 1~2 字节长度前缀（255 内 1B） |
| 场景 | 定长：md5(32)、身份证(18)、国家代码(2) | 长度弹性大的字段 |
| 修改行溢出 | 无 | 可能引发行迁移 |

- `varchar(50)` 的 50 是**字符数**（不是字节；4.0 之前是字节），utf8mb4 下实际最大字节数 = 50×4 + 长度前缀；行总长受 65535 字节限制。
- **null 相关**：
  - `null != null`，判断用 `is null / is not null`；
  - count(字段) 不统计 NULL 行；
  - null 值需要额外标记位，且含 NULL 的列难以做某些索引优化；
  - 惯例：能用 not null + 默认值就用（语义明确、索引友好），但"not null 一定省空间/更快"并非绝对，主因是语义清晰。

### drop / delete / truncate

| | drop | truncate | delete |
|--|------|----------|--------|
| 级别 | 删表+结构 | 清空表（保留结构） | 按条件删行 |
| 事务/回滚 | DDL，不可回滚 | 不可回滚 | DML，可回滚 |
| 触发器/where | 无 | 无 | 都有 |
| 速度/重置 | 快 | 快，重置自增值 | 逐行删，自增值保留 |

## Q21: 为什么推荐自增主键？自增 ID 用完了怎么办？

### 自增主键的好处

- **顺序插入**：每次追加到最后一个数据页，无随机 IO、无页分裂；随机主键（UUID/雪花乱序部分）导致频繁页分裂、缓存命中率低、空间碎片。
- 主键短：所有二级索引叶子都存主键，主键越长二级索引越占空间。

### 自增用完怎么办

| 类型 | 上限 | 方案 |
|------|------|------|
| int unsigned | 约 42.9 亿 | 一般够；不够时 `alter table ... modify id bigint unsigned`（8.0 支持 instant/inplace 视情况，一般用新表双写迁移） |
| bigint unsigned | 约 1844 京（1.8×10^19） | 基本用不完（每秒 10 亿也要 58 万年） |
| 自增锁 | — | 8.0 默认 `innodb_autoinc_lock_mode=2`（交错模式），配合批量插入性能好 |

- 业务主键（订单号等）与物理主键分离：物理主键用自增 bigint 保性能，业务编号单独一列加唯一索引（也可以业务号本身做分布式 ID 保趋势递增）。

### 分库分表下的全局唯一 ID

- 雪花算法（时间戳+机器位+序列，趋势递增）、号段模式（DB 批量取段）、Redis INCR、Leaf/UidGenerator。

## Q22: 什么情况下需要分库分表？怎么拆？

### 什么时候

单表数据量过大（经验值：B+ 树层级 3~4、行数千万级为界，具体看行宽和查询模式）、QPS/TPS 超过单实例上限、磁盘/备份等运维成本不可接受。

### 拆分方式

| 方向 | 内容 | 收益/代价 |
|------|------|-----------|
| 垂直分库 | 按业务域拆库（订单库、用户库） | 业务解耦、专库专用；跨库事务 |
| 垂直分表 | 大字段/访问频率差异拆表（详情拆出去） | 减小行宽、缓存效率高 |
| 水平分库分表 | 同结构按 sharding key 拆多库多表 | 解决量与并发；路由复杂、跨片查询/事务难 |

### 分片键与代价

- 选**查询高频字段**做 sharding key（订单：user_id 或 order_id），避免数据倾斜；
- 分布式 ID（雪花）保证全局唯一且趋势递增；
- 带来问题及解法：跨片分页（业务规避/聚合中间层）、跨片 join（冗余字段/宽表/异构索引如 ES）、跨库事务（消息最终一致、本地消息表、Seata）、扩容（一致性哈希/翻倍扩容+双写迁移）。

### 关键理解（加分点）

- 分库分表是最后手段：先索引优化 → 读写分离 → 缓存 → 冷热分离/归档 → 再考虑分片；有条件上分布式数据库（TiDB 等）可省掉应用层分片复杂度。

## Q23: 三大范式是什么？什么时候反范式？

- **1NF**：字段不可再分（原子性）。
- **2NF**：在 1NF 上，非主键列**完全依赖**主键（消除部分依赖，联合主键场景）。
- **3NF**：在 2NF 上，非主键列**直接依赖**主键（消除传递依赖，如"部门名"依赖"部门 ID"再依赖主键，应拆表）。

### 反范式

为读性能适度冗余：冗余高频读取字段（订单表冗余商品名）、宽表、计数列。代价是**一致性维护成本**（同事务更新或异步补偿）。互联网场景"读多写少 + 量大"，普遍是"3NF 设计为底，按查询反范式优化"。

## Q24: InnoDB 和 MyISAM 的区别？为什么默认换成了 InnoDB？

| 对比点 | InnoDB | MyISAM |
|--------|--------|--------|
| 事务 | 支持 | 不支持 |
| 锁 | 行级锁（+表锁） | 表级锁 |
| 崩溃恢复 | redo log 支持 crash-safe | 不支持，崩了可能表损坏 |
| 外键 | 支持 | 不支持 |
| MVCC | 支持 | 不支持 |
| count(*) 全表 | 需扫描 | 存了总数，O(1) |
| 聚簇索引 | 数据即主键索引 | 索引与数据分离 |

- 默认切换原因：Web 应用普遍需要事务 + 高并发写 + 崩溃安全，MyISAM 表锁 + 无事务是硬伤；count 优势可通过计数表解决。

## Q25: 一句话快问快答（高频送分/送命题）

| 问题 | 要点 |
|------|------|
| 数据库三大日志顺序？ | 执行前写 undo → 更新 buffer pool + 写 redo(prepare) → 写 binlog → redo(commit) |
| drop 误删怎么恢复？ | 延迟从库/全量备份+binlog 恢复（`mysqlbinlog --start-position` 回放到误操作前） |
| select * 的问题？ | 无法覆盖索引（强制回表）、网络/内存放大、加列后缓存与绑定变量失效 |
| in 和 exists？ | 小表驱动大表：外表小用 in（子查询走索引），外表大用 exists；8.0 优化器基本自动转换，语义优先 |
| union 和 union all？ | union 去重（临时表排序开销），union all 不去重；能确定无重复就用 all |
| 视图/临时表区别？ | 视图是 SQL 快照（逻辑），物化需自己建表；临时表会话级，复杂排序/分组时内部也可能用内部临时表 |
| mysql 长连接的坑？ | 内存涨（执行期间的临时缓存在连接对象上，断了才释放）→ 定期断开或 mysql_reset_connection；8.0 后部分缓解 |
| 主键为什么不推荐业务字段？ | 业务变更风险、过长导致二级索引膨胀、非顺序插入页分裂 |
| mysql 默认端口/配置文件？ | 3306；`/etc/my.cnf` 或 `/etc/mysql/my.cnf`；`show variables like '%xxx%'` 查参数 |
| 悲观锁 vs 乐观锁？ | 悲观：for update 先锁；乐观：版本号 `update ... set v=v+1 where id=? and v=?`，重试，读多写少/冲突少场景 |
| 锁等待排查？ | `show processlist` + `performance_schema.data_lock_waits`（8.0）或 `sys.innodb_lock_waits` 视图 |
| 索引会是越多越好吗？ | 不是：写放大、空间、优化器选错风险；定期 `sys.schema_unused_indexes` 清理无用索引 |
