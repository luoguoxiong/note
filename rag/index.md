# RAG 面试题整理

> 按主题分组：数据与切片 → 检索策略 → 效果优化与评估 → 性能优化。

## 一、数据与切片

### 1. RAG 知识库有多大？切片是怎么设计的？

**数据规模**

- 原始文档约 3000 份，经解析、清洗、结构化切分后生成约 15 万条 Chunk，平均每份文档约 50 条
- 每个 Chunk 约 1000 字符，Overlap 150

**切片策略：按文档类型差异化处理，不做一刀切的固定长度切分**

- 制度、操作手册：优先按标题、章节和段落切分；过长段落再用固定窗口二次切分，并设置 Overlap，减少跨 Chunk 的语义断裂
- FAQ：尽量保持完整问答
- 表格：保留表头和业务字段之间的对应关系

**元数据与入库**

- 每个 Chunk 保留 document_id、章节路径、chunk_index 等元数据，生成 Embedding 后写入向量数据库

**要点**

- 15 万条是实际切片后的数据规模，不是预先固定的数量
- 后续结合 Recall@K、Hit Rate 和检索失败案例，持续调整 Chunk 大小、重叠比例和切片规则，在召回质量和检索成本之间取得平衡

### 2. RAG 支持哪些文档？上传后如何切片和落库？

**支持的格式**

- PDF：pdf-parse 解析，带硬换行段落还原
- DOCX：mammoth 提取文本
- Markdown：取首个一级标题作 title，并标记 language
- 纯文本

**入库流程**

1. 解析：按类型选择 Parser，提取纯文本 + 标题 + 元数据
2. 归一化：去空白、统一换行——让同一内容算出稳定的内容哈希，天然去重
3. 单事务落三张表：documents + document_versions（原文暂存 PG）+ index_document 的 Job；任一失败整体回滚，不会出现"有文档没任务"的孤儿状态
4. 返回后由 Worker 异步消费，做真正的切片和索引——上传响应快，失败可重试

**切片策略**

1. 按文档类型选不同 Splitter，统一输出 parent/child 两级结构（Parent-Child Retrieval）
2. Markdown 专用（结构感知）：先按 #~###### 标题分节，标题作为 parent 的语义前缀；节内再拆块——代码块、表格整体保留为一个 child（拆开会破坏语义），普通段落按中英文句号分句后聚合
3. text/PDF/DOCX（通用）：按句号分句 → 句子聚合成 child → child 聚合成 parent；句子保持完整，不做字符级硬切，避免语义碎片化

**两级目标尺寸**

- child ≈ 400 字符：检索单元，粒度小、召回准
- parent ≈ 2000 字符：上下文单元

**为什么用两级**：child 小，向量检索精准；但小 chunk 缺上下文，命中 child 后回表用它的 parent 喂给 LLM——召回精度和上下文完整性同时拿到。

### 3. PDF 中的图片和表格如何处理？

**总体原则**：不会把 PDF 中的图片和表格统一当成普通文本切片，而是先做版面分析和内容类型识别。

**普通正文**：按照标题和语义边界进行切片。

**扫描件和图片**

- 通过 OCR 提取文字
- 流程图、图表等复杂内容使用多模态模型进行语义解析
- 保留原图、页码和来源信息

**表格**

- 重点保留表头、行列关系、单位和适用条件
- 小表格整体存储；大表格按行组或业务实体切分，并在每个 chunk 中重复必要的表头，避免检索后出现数据与字段错位

**索引与下游使用**

- 文本描述用于关键词和向量检索，同时保留结构化数据与原始文档的映射
- 运费、价格、区间规则等要求精确计算的场景，优先通过结构化查询或程序计算，而不是完全依赖大模型生成

## 二、检索策略

### 4. 为什么检索用语义和 BM25 两种方式？

| 检索方式 | 擅长 | 短板 |
| --- | --- | --- |
| 向量（语义）检索 | 同义词、改写、口语化 query，"意思相近"即可命中 | 专有名词会被"平均"进语义空间，漏掉精确匹配；未见过的新词/冷词 embedding 质量差 |
| BM25（关键词）检索 | 专有名词、错误码、型号、API 名等必须字面命中的词，精确且可解释 | 词表不同就召回不了；受同义改写、中文分词影响大 |

结论：两者互补——向量管语义泛化，BM25 管专有名词和精确匹配，混合检索解决单路召回盲区。

### 5. 用的什么向量库？如何选型？

**主流方案对比**

| 方案 | 核心优势 | 适用场景 | 主要取舍 |
| --- | --- | --- | --- |
| Qdrant | 向量检索、元数据过滤、多向量检索能力 | 企业 RAG、多租户知识库 | 需要独立部署和维护 |
| pgvector | 与 PostgreSQL、SQL、事务和权限体系集成 | 已使用 PostgreSQL 的中小规模 RAG | 向量负载可能与业务查询争抢资源 |
| Milvus | 面向大规模向量检索的分布式架构 | 海量向量、高并发检索 | 部署、扩缩容和运维复杂度较高 |
| Weaviate | 向量检索与混合搜索能力集成 | 语义搜索、关键词与向量混合检索 | 需要评估其完整功能与现有技术栈的匹配度 |
| Pinecone | 托管服务，减少底层运维 | 希望减少自建数据库运维的团队 | 服务费用、云平台依赖 |

**选型思路**

- 考虑维度：数据规模、检索能力、多租户过滤、运维复杂度
- 需求：向量检索 + 按租户、文档版本、权限过滤；支持关键词与向量混合检索；检索服务可独立扩展
- 结论：优先选择 Qdrant。若业务已深度依赖 PostgreSQL，且数据规模和查询负载适合单库承载，pgvector 可降低基础设施复杂度；未来出现更大规模分布式检索需求时再评估 Milvus
- 原则：不只凭产品特性决定选型，而是用真实业务查询，对 Recall@K、P95 延迟、过滤后的召回率和资源消耗做压测

## 三、效果优化与评估

### 6. 遇到过模型理解不对的情况吗？怎么解决的？

**定位思路**：不简单归因于模型能力不足，而是把问题拆成问题理解、证据检索、答案生成三个环节，先定位错误发生在哪一层，再针对性优化。

**1. 优化问题理解**

- 检索前增加 Query Analyzer，做意图识别和关键条件提取（加班类型、适用部门、审批条件等）
- 口语化问题（如"周末加班能不能调休"）转换成更适合检索的查询，并补充"加班审批""调休申请条件"等相关检索词

**2. 优化检索和上下文组织**

- 关键词检索 + 向量检索混合，RRF 融合结果，再用 Reranker 对候选文档做相关性排序
- 尽量保留规则的适用范围、例外条件和前置要求，避免只召回"加班可以调休"这类局部片段，却遗漏后面的限制条款

**3. 约束生成并建立评估机制**

- System Prompt 明确要求：只依据检索到的证据回答，区分一般规则和特殊规则；证据不足时明确说明，不允许自行补充制度
- 回答带引用编号，可追溯到原始文档和具体片段
- 用一组典型问题做回归测试，重点检查问题理解是否正确、相关证据是否召回、回答是否忠于证据；结合 Faithfulness、Recall@K 和人工抽检定位问题

### 7. 如何进行 RAG 调优？

核心原则：一切调优必须由评估体系驱动。分效果调优和性能调优两个层面。

**一、前提：先建评估体系，再谈调优**

- Golden Dataset：每条查询带黄金 chunk（goldChunkIds）和参考答案，数据集绑定 indexVersion 和 embeddingVersion
- 定义 8 项指标：检索侧 Recall@K / Hit Rate / MRR / NDCG；生成侧 Context Precision / Context Recall / Faithfulness / Answer Relevance
- 回归门禁：每次调参跑评估，任一指标低于基线 ×(1−0.1) 即 FAIL，产出 Markdown 报告阻断合并——保证调优不会"按下葫芦浮起瓢"

**二、效果调优：按数据流水线逐层优化**

1. **切分层（影响最大的第一步）**
    - Parent-Child 两级分块：child 400 字符做检索单元（小而准），parent 2000 字符做上下文单元（大而全），child 带 80 字符 overlap；命中 child 后回填 parent 给 LLM，兼顾检索精度和上下文完整性
    - 结构感知切分：Markdown 按标题分节、标题作语义前缀；表格和代码块整体保留绝不拆散；按句子聚合而非字符硬切，避免句子截断
    - chunk 用内容哈希做稳定 ID，幂等落库，支持增量更新
2. **召回层：混合检索解决单路召回盲区**
    - 向量（Qdrant Cosine）+ 关键词（OpenSearch BM25）双路并行：向量管语义泛化，BM25 管专有名词/精确匹配（向量对代码标识符、型号这类 token 很弱）
    - RRF 融合（k=60）做去量纲合并，不依赖两路分数可比
    - 每路 3 秒竞速超时，关键词路挂了降级纯向量，保证可用性
    - metadata 过滤三重保障：Qdrant payload filter + OpenSearch terms filter + 回表二次校验，多租户/多版本不会串数据
3. **查询智能层：改 query 而不是只改检索**
    - Query Analyzer → Router → Transform 管线，规则优先（cheap-first，零 LLM 开销），低置信才升级 LLM
    - 三种变换互斥、按需选用：Rewrite（指代消解，把"它怎么样"改写成自包含查询）、MultiQuery（宽泛问题扩展 3 个变体并行召回，变体间再做一层 RRF）、HyDE（多跳/概念性问题生成假设答案去检索，弥补 query 与文档的语义鸿沟）
4. **重排层：精排解决"召回对但排序差"**
    - RRF 融合后用 LLM-as-Reranker 对候选重排序（接口抽象成 Reranker，可平滑换 bge-reranker/Cohere）
    - 省 token：少于 4 条证据跳过重排
5. **生成层：防幻觉 + 上下文工程**
    - 单证据截断 1500 字符、上下文总预算 8000 字符，控制噪声
    - System Prompt 强约束"仅依据证据回答，证据不足明确说明"；回答带 [1][2] 编号引用回链到具体 chunk，用 Faithfulness 指标闭环验证
6. **必要时上 GraphRAG**
    - 实体关系/多跳类问题路由到 Neo4j 做 N-Hop 子图遍历或社区摘要全局检索
    - 不是所有查询都进图，由 Router 按意图路由，避免图检索的高成本

**三、性能调优：一个真实案例**

- 压测发现 /search 平均 13.45s（检索 5.76s + 生成 7.69s），针对性优化：
    - MultiQuery 的多次 embedding 批量合并为 1 次 API 调用（原来 N 次串行）
    - 重排统一为 1 次
    - 收紧上下文预算 + maxTokens 1024
    - Redis 语义结果缓存（TTL 600s，documentIds 进缓存键，防版本切换命中旧答案）
- 结果：简单查询降到 2~4s，重复命中缓存约 5ms

**四、工程兜底（区分玩具和生产的部分）**

- PostgreSQL 是唯一事实源，Qdrant/OpenSearch/Neo4j 全是可重建的派生索引——换 embedding 模型、改 chunk 策略后可全量重索引
- Outbox 事件 + Reconciliation 对账循环保证索引最终一致，消费失败自愈
- 全链路降级：LLM 挂了回退确定性实现，图检索挂了降级无子图

### 8. 评测集的标准答案是怎么来的？

来源：真实业务问题抽样 + 依据原始文档人工标注 + 双人复核。

1. 从客服咨询、员工提问记录、历史搜索日志中收集问题；历史数据不足时，由业务人员根据制度文档补充典型问题
2. 由熟悉业务的人员对照原始制度，记录正确答案、对应的文档和章节，以及能够支持答案的标准证据片段
3. 容易混淆、涉及多个制度或存在版本差异的问题，由第二位审核人员复核；无法从文档确认的问题标记为"证据不足"，不强行编造答案
4. 固定问题、标准答案、标准证据和文档版本；后续调整 Chunk 大小、检索算法、Reranker 或 Prompt 时，使用同一套评测集进行对比

## 四、性能优化

### 9. 有没有延迟特别高的场景？如何解决？

**定位：用数据说话**

- 给 /search 链路打点，latencyMs、retrievalMs、generationMs 落在 retrieval_logs 表
- 压测发现 P50 是 13.45 秒：检索 5.76s + 生成 7.69s
- 拆开看根因：数据库和向量索引都不慢，慢在一次请求里串行了 4~6 次外部 LLM/API 调用，每次火山方舟往返 1~3 秒，叠加出来的

**三个最慢场景**

1. Multi Query：宽泛问题扩展成 N 个变体，原实现是每个变体各付一次 embedding、各做一次 LLM 重排、各开一个回表事务，N 倍放大
2. 低置信查询：规则路由判低置信后，要先调 LLM Analyzer 再调 LLM Router，两次串行往返之后才真正开始检索
3. 长尾没兜底：LLM 重排没有容错，一失败整个请求 500；检索超时配置声明了但没生效，下游一慢就无限等；生成段没上限没流式，用户干等

**解决方案：四层**

1. **削调用次数**：变体的 embedding 批量合并成一次；重排从每路一次改成 RRF 融合后统一一次；N 路召回不回表、融合后统一回表一次；Analyzer 和 Router 合并成一次 LLM 调用直接输出"分析+路由"——多查询场景从 2N 次调用降到常数次
2. **削单次开销**：证据截断加总预算控制 prompt 大小，max_tokens 限输出；Redis 结果缓存，重复查询 5 毫秒返回
3. **削长尾**：每路检索加竞速超时，3 秒降级——向量路超时就退纯关键词，反过来也一样；重排失败降级到本地确定性重排。保证下游故障时是"变慢"而不是"雪崩"
4. **削感知延迟**：规划中的流式输出——检索完先把引用推给前端，答案流式吐，总耗时不变但首屏从 8 秒变 2 秒

**效果与方法论**

- 简单查询从 13.45s 降到 2~4s
- 方法论：cheap-first——能用规则的不用 LLM，能合并的调用不串行，所有优化都有打点数据可以回归验证
