1. Rag 知识库有多大？切片是怎么样设计的？召回率怎么样？

我们目前的 RAG 知识库主要覆盖公司考勤管理场景，包括考勤制度、请假规则、加班调休、部门差异化规则以及考勤 FAQ，总计约 175 份文档。

召回率方面，我不会单纯依赖线上用户反馈，而是通过构建考勤领域的标准测试集，评估检索系统对相关知识的召回能力。

**第一，构建评估集。** 从实际考勤问题中整理测试问题，例如“年假未休完是否可以折现”“忘记打卡如何补卡”“某部门弹性工作制如何计算迟到”等。为每个问题标注对应的标准文档、章节或 Chunk，作为 Ground Truth。

**第二，建立评估指标。** 主要关注 Recall@K 和 Hit Rate@K。Recall@K 用来衡量 Top-K 检索结果覆盖了多少相关知识；Hit Rate@K 用来衡量 Top-K 结果中是否至少命中一条相关知识。同时结合 MRR 或 NDCG 评估相关内容的排序质量。

**第三，进行分层评估。** 除了整体指标，还会针对考勤制度、请假、加班调休、部门特殊规则等场景分别统计召回效果，重点关注跨部门规则冲突、相似问题和长文档章节定位等容易漏召回的场景。

**第四，持续优化。** 检索链路采用 Child Chunk 召回、Parent Chunk 补充上下文的方式，在保持召回粒度较小的同时，避免回答时缺少完整规则；同时通过关键词与向量混合检索、Reranker 重排以及 Top-K 参数调优，提高相关知识的召回和排序质量。

每次调整切片策略或检索参数后，都会在同一套测试集上进行回归评估，确保召回效果有实际数据支撑，而不是仅凭主观判断。



2. 有没有延迟特别高的场景？如何解决?


有的，这个我印象很深，因为我们是用数据定位出来的。我们给 /search 链路做了打点，latencyMs、retrievalMs、generationMs 都落在 retrieval_logs 表里，压测发现 P50 是 13.45 秒，其中检索 5.76s、生成 7.69s。拆开看根因很有意思：数据库和向量索引都不慢，慢的是一次请求里串行了 4~6 次外部 LLM/API 调用，每次火山方舟往返 1~3 秒，叠出来的。

最慢的有三个场景：

第一个是 Multi Query。宽泛问题会扩展成 N 个变体，原实现是每个变体各付一次 embedding、各做一次 LLM 重排、各开一个回表事务，N 倍放大。

第二个是低置信查询。规则路由判低置信后，要先调 LLM Analyzer 再调 LLM Router，两次串行往返之后才真正开始检索。

第三个是长尾没兜底。LLM 重排没有容错，一失败整个请求 500；检索超时配置声明了但没生效，下游一慢就无限等；生成段没上限没流式，用户干等。

解决我分了四层：

削调用次数：变体的 embedding 批量合并成一次；重排从每路一次改成 RRF 融合后统一一次；N 路召回不回表、融合后统一回表一次；Analyzer 和 Router 合并成一次 LLM 调用直接输出“分析+路由”。这样多查询场景从 2N 次调用降到常数次。
削单次开销：证据截断加总预算控制 prompt 大小，max_tokens 限输出；再加 Redis 结果缓存，重复查询 5 毫秒返回。
削长尾：每路检索加竞速超时，3 秒降级——向量路超时就退纯关键词，反过来也一样；重排失败降级到本地确定性重排。保证下游故障时是“变慢”而不是“雪崩”。
削感知延迟：这一步是规划中的流式输出——检索完先把引用推给前端，答案流式吐，总耗时不变但首屏从 8 秒变 2 秒。
最后效果是简单查询从 13.45s 降到 2~4s。方法论上我的原则是 cheap-first：能用规则的不用 LLM，能合并的调用不串行，所有优化都有打点数据可以回归验证。

3. 如何进行Rag 调优？
RAG 调优分为两个层面——效果调优和性能调优，核心原则是一切调优必须由评估体系驱

一、先建评估体系，再谈调优（前提）
建 Golden Dataset：每条查询带黄金 chunk（goldChunkIds）和参考答案，数据集绑定 indexVersion 和 embeddingVersion
定义 8 项指标：检索侧 Recall@K / Hit Rate / MRR / NDCG，生成侧 Context Precision / Context Recall / Faithfulness / Answer Relevance
回归门禁：每次调参跑评估，任一指标低于基线 ×(1−0.1) 就 FAIL，产出 Markdown 报告阻断合并——保证“调优”不会按下葫芦浮起瓢

二、效果调优：按数据流水线逐层优化
1. 切分层（Chunking）——影响最大的第一步

用 Parent-Child 两级分块：child 400 字符做检索单元（小而准），parent 2000 字符做上下文单元（大而全），child 带 80 字符 overlap；命中 child 后回填 parent 给 LLM，兼顾检索精度和上下文完整性
结构感知切分：Markdown 按标题分节、标题作语义前缀；表格和代码块整体保留绝不拆散；按句子聚合而非字符硬切，避免句子截断
chunk 用内容哈希做稳定 ID，幂等落库，支持增量更新
2. 召回层：混合检索解决单路召回盲区

向量（Qdrant Cosine）+ 关键词（OpenSearch BM25）双路并行：向量管语义泛化，BM25 管专有名词/精确匹配（向量对代码标识符、型号这类 token 很弱）
RRF 融合（k=60）做去量纲合并，不依赖两路分数可比
每路 3 秒竞速超时，关键词路挂了降级纯向量，保证可用性
metadata 过滤做了三重保障：Qdrant payload filter + OpenSearch terms filter + 回表二次校验，多租户/多版本不会串数据
3. 查询智能层：改 query 而不是只改检索

Query Analyzer → Router → Transform 管线，规则优先（cheap-first，零 LLM 开销），低置信才升级 LLM
三种变换互斥，按需选用：Rewrite（指代消解，把“它怎么样”改写成自包含查询）、MultiQuery（宽泛问题扩展 3 个变体并行召回，变体间再做一层 RRF）、HyDE（多跳/概念性问题生成假设答案去检索，弥补 query 与文档的语义鸿沟）

4. 重排层：精排解决“召回对但排序差”

RRF 融合后用 LLM-as-Reranker 对候选重排序（接口抽象成 Reranker，可平滑换 bge-reranker/Cohere）
省 token：少于 4 条证据跳过重排；

5. 生成层：防幻觉 + 上下文工程

单证据截断 1500 字符、上下文总预算 8000 字符，控制噪声
System Prompt 强约束“仅依据证据回答，证据不足明确说明”；回答带 [1][2] 编号引用回链到具体 chunk，用 Faithfulness 指标闭环验证

6. 必要时上 GraphRAG：实体关系/多跳类问题路由到 Neo4j 做 N-Hop 子图遍历或社区摘要全局检索——不是所有查询都进图，由 Router 按意图路由，避免图检索的高成本。

三、性能调优：一个真实案例
压测发现 /search 平均 13.45s（检索 5.76s + 生成 7.69s），做了针对性优化：

MultiQuery 的多次 embedding 批量合并为 1 次 API 调用（原来是 N 次串行）
重排统一为 1 次
收紧上下文预算 + maxTokens: 1024
Redis 语义结果缓存（TTL 600s，documentIds 进缓存键防版本切换命中旧答案）
结果：简单查询降到 2~4s，重复命中缓存约 5ms。

四、工程兜底（区分玩具和生产的部分）
PostgreSQL 是唯一事实源，Qdrant/OpenSearch/Neo4j 全是可重建的派生索引——换 embedding 模型、改 chunk 策略后可全量重索引
Outbox 事件 + Reconciliation 对账循环保证索引最终一致，消费失败自愈
全链路降级：LLM 挂了回退确定性实现、图检索挂了降级无子图
