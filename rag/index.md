# RAG 

> 按主题分组：RAG 原理 → 数据与切片 → 检索策略 → 效果优化与评估 → 性能优化 → 工程化与部署。

## 〇、RAG 原理

### 0. RAG 的工作原理是什么？与直接对 LLM 微调相比，主要解决了什么问题、有哪些优势？

**工作原理：模型参数不动，外挂知识库，推理时按需检索并注入上下文——把"闭卷考试"变成"开卷考试"**

离线索引：

1. 解析与清洗：PDF/DOCX/Markdown 等提取纯文本、标题和元数据
2. 切片：按文档类型差异化切分（如 parent/child 两级），对 chunk 生成 Embedding
3. 入库：向量 + 元数据写入向量库，同时建 BM25 关键词索引

在线问答：

1. Query 理解：意图识别、改写、扩展（Query Analyzer）
2. 检索：向量 + 关键词混合召回 → RRF 融合 → Reranker 精排
3. 组装上下文：命中的 chunk 和 System Prompt 拼成 prompt，证据带编号
4. 生成：LLM 被约束"仅依据证据回答"，答案带引用可回链原文

**与微调的本质区别**：微调是把知识"写进"模型权重（改参数），RAG 是把知识放在模型外部、推理时临时注入（改上下文）。

**微调的四个根本局限，正是 RAG 解决的问题**

1. 知识时效性：制度文档频繁更新，微调要重新标注、训练、评估、部署，周期以天/周计；RAG 只需重新索引，分钟级生效
2. 私有知识注入：企业内部文档不在预训练语料中，用微调注入事实性知识需要大量标注数据，且容易把知识"背糊"；RAG 检索命中即可用
3. 幻觉与可溯源：微调无法保证答案有出处，错了也查不到来源；RAG 把生成约束在检索证据内，引用可回链到具体文档片段
4. 权限与多租户：微调把知识焊死在参数里，做不到按用户隔离；RAG 在检索层做 metadata 过滤即可实现租户/版本隔离

**优势对比**

| 维度 | RAG | 微调 |
| --- | --- | --- |
| 知识更新 | 重索引即可，分钟级 | 重训练 + 重部署，天级 |
| 事实准确性 | 证据约束 + 引用可溯源 | 无法溯源，易编造或过时 |
| 成本 | 只有索引和检索成本 | 标注 + GPU 训练 + 每次更新重训 |
| 通用能力 | 无损，无灾难性遗忘 | 可能遗忘原有通用能力 |
| 数据隔离 | 检索层过滤，天然支持多租户/多版本 | 参数内知识无法按用户隔离 |
| 可解释性 | 引用回链原文，可审计 | 黑盒 |

**什么时候才轮到微调**：不是为了注入知识，而是为了改变行为——固定输出格式、语气风格、领域术语适配、小模型蒸馏降本。实践中常组合：微调管"怎么答"（能力与格式），RAG 管"答什么"（知识与事实）。本项目的场景——制度文档持续更新、需按租户和版本隔离、答案必须可审计——微调都满足不了，所以选 RAG。

## 一、数据与切片

### 1. RAG 知识库有多大？切片是怎么设计的？

**数据规模**

- 原始文档约 3000 份，经解析、清洗、结构化切分后生成约 15 万条 Chunk，平均每份文档约 50 条
- 每个 Chunk 约 1000 字符，Overlap 150

**切片策略：按文档类型差异化处理，不做一刀切的固定长度切分**

- 制度、操作手册：优先按标题、章节和段落切分；过长段落再用固定窗口二次切分，并设置 Overlap，减少跨 Chunk 的语义断裂
- FAQ：尽量保持完整问答
- 表格：保留表头和业务字段之间的对应关系

**元数据与入库**

- 每个 Chunk 保留 document_id、章节路径、chunk_index 等元数据，生成 Embedding 后写入向量数据库

**要点**

- 15 万条是实际切片后的数据规模，不是预先固定的数量
- 后续结合 Recall@K、Hit Rate 和检索失败案例，持续调整 Chunk 大小、重叠比例和切片规则，在召回质量和检索成本之间取得平衡

### 2. RAG 支持哪些文档？上传后如何切片和落库？

**支持的格式**

- PDF：pdf-parse 解析，带硬换行段落还原
- DOCX：mammoth 提取文本
- Markdown：取首个一级标题作 title，并标记 language
- 纯文本

**入库流程**

1. 解析：按类型选择 Parser，提取纯文本 + 标题 + 元数据
2. 归一化：去空白、统一换行——让同一内容算出稳定的内容哈希，天然去重
3. 单事务落三张表：documents + document_versions（原文暂存 PG）+ index_document 的 Job；任一失败整体回滚，不会出现"有文档没任务"的孤儿状态
4. 返回后由 Worker 异步消费，做真正的切片和索引——上传响应快，失败可重试

**切片策略**

1. 按文档类型选不同 Splitter，统一输出 parent/child 两级结构（Parent-Child Retrieval）
2. Markdown 专用（结构感知）：先按 #~###### 标题分节，标题作为 parent 的语义前缀；节内再拆块——代码块、表格整体保留为一个 child（拆开会破坏语义），普通段落按中英文句号分句后聚合
3. text/PDF/DOCX（通用）：按句号分句 → 句子聚合成 child → child 聚合成 parent；句子保持完整，不做字符级硬切，避免语义碎片化

**两级目标尺寸**

- child ≈ 400 字符：检索单元，粒度小、召回准
- parent ≈ 2000 字符：上下文单元

**为什么用两级**：child 小，向量检索精准；但小 chunk 缺上下文，命中 child 后回表用它的 parent 喂给 LLM——召回精度和上下文完整性同时拿到。

### 3. PDF 中的图片和表格如何处理？

**总体原则**：不会把 PDF 中的图片和表格统一当成普通文本切片，而是先做版面分析和内容类型识别。

**普通正文**：按照标题和语义边界进行切片。

**扫描件和图片**

- 通过 OCR 提取文字
- 流程图、图表等复杂内容使用多模态模型进行语义解析
- 保留原图、页码和来源信息

**表格**

- 重点保留表头、行列关系、单位和适用条件
- 小表格整体存储；大表格按行组或业务实体切分，并在每个 chunk 中重复必要的表头，避免检索后出现数据与字段错位

**索引与下游使用**

- 文本描述用于关键词和向量检索，同时保留结构化数据与原始文档的映射
- 运费、价格、区间规则等要求精确计算的场景，优先通过结构化查询或程序计算，而不是完全依赖大模型生成

## 二、检索策略

### 4. 为什么检索用语义和 BM25 两种方式？

| 检索方式 | 擅长 | 短板 |
| --- | --- | --- |
| 向量（语义）检索 | 同义词、改写、口语化 query，"意思相近"即可命中 | 专有名词会被"平均"进语义空间，漏掉精确匹配；未见过的新词/冷词 embedding 质量差 |
| BM25（关键词）检索 | 专有名词、错误码、型号、API 名等必须字面命中的词，精确且可解释 | 词表不同就召回不了；受同义改写、中文分词影响大 |

结论：两者互补——向量管语义泛化，BM25 管专有名词和精确匹配，混合检索解决单路召回盲区。

### 5. 用的什么向量库？如何选型？

**主流方案对比**

| 方案 | 核心优势 | 适用场景 | 主要取舍 |
| --- | --- | --- | --- |
| Qdrant | 向量检索、元数据过滤、多向量检索能力 | 企业 RAG、多租户知识库 | 需要独立部署和维护 |
| pgvector | 与 PostgreSQL、SQL、事务和权限体系集成 | 已使用 PostgreSQL 的中小规模 RAG | 向量负载可能与业务查询争抢资源 |
| Milvus | 面向大规模向量检索的分布式架构 | 海量向量、高并发检索 | 部署、扩缩容和运维复杂度较高 |
| Weaviate | 向量检索与混合搜索能力集成 | 语义搜索、关键词与向量混合检索 | 需要评估其完整功能与现有技术栈的匹配度 |
| Pinecone | 托管服务，减少底层运维 | 希望减少自建数据库运维的团队 | 服务费用、云平台依赖 |

**选型思路**

- 考虑维度：数据规模、检索能力、多租户过滤、运维复杂度
- 需求：向量检索 + 按租户、文档版本、权限过滤；支持关键词与向量混合检索；检索服务可独立扩展
- 结论：优先选择 Qdrant。若业务已深度依赖 PostgreSQL，且数据规模和查询负载适合单库承载，pgvector 可降低基础设施复杂度；未来出现更大规模分布式检索需求时再评估 Milvus
- 原则：不只凭产品特性决定选型，而是用真实业务查询，对 Recall@K、P95 延迟、过滤后的召回率和资源消耗做压测

### 6. 嵌入模型怎么选？评估 Embedding 模型的好坏有哪些指标？

**选型流程：榜单初筛 → 业务数据实测 → 工程约束收敛**

1. **榜单初筛**：看 MTEB / C-MTEB（中文）的 Retrieval 子榜，圈定候选；不迷信综合榜，检索任务强才是关键
2. **业务数据实测（决定性一步）**：拿自建 Golden Dataset 跑 Recall@K / Hit Rate / NDCG。榜单分数和业务语料上的表现经常不一致——通用语料强不代表制度、FAQ 这类垂直语料强
3. **工程约束收敛**：
    - 上下文窗口：token 上限必须覆盖最长 chunk（child 400 字符 + overlap，留余量），否则截断丢语义
    - 向量维度：维度越高，向量库存储、内存和检索开销越大
    - 部署形态：API（省运维，但有网络开销和数据出域问题）vs 本地开源（bge/gte 系列，可控、可微调）
    - 语言能力：中英混合文档要求多语言支持
    - 配套生态：是否有同系列 Reranker、是否支持稠密+稀疏向量（如 bge-m3）
4. **一致性约束**：query 和文档必须用同一个模型编码；部分模型（bge/e5 系列）要求 query 侧加指令前缀，漏掉会掉点；换模型 = 全量重索引，新旧向量不可混用

**评估指标：三层**

1. **检索效果（核心，用真实业务评测集测）**
    - Recall@K：前 K 条召回中命中相关 chunk 的比例，最贴近业务效果
    - Hit Rate：top-K 至少命中一条的比例，衡量"能不能答"
    - MRR：首个相关结果排名倒数的均值，衡量排序质量
    - NDCG@K：考虑分级相关性和位置折损，刻画更细腻
2. **模型内在质量**
    - MTEB / C-MTEB Retrieval 分数：多任务基准，做初筛参考
    - 区分度：相似对与不相似对的相似度分布能否拉开，决定相似度阈值好不好定
    - 鲁棒性：错别字、口语化改写、长尾词下的稳定性
3. **工程与成本**
    - 延迟与吞吐：批量编码速度决定 15 万 chunk 的索引构建时间，在线编码延迟影响 P95
    - 单位成本：API 定价或 GPU 资源占用
    - 向量维度：存储与内存占用

**结合本项目**：评测集绑定 embeddingVersion；换模型走全量重索引（PostgreSQL 是唯一事实源，向量库只是可重建的派生索引），用同一套 Golden Dataset 做新旧模型对比，指标不回退才切换。

### 7. 如何提高 RAG 的召回率？

**先定位再优化：用 Golden Dataset 上的 Recall@K / Hit Rate 做分层归因——是 query 表达不出来、内容不在库里，还是检索不回来？按数据流水线从数据层到查询层逐层加强。**

**1. 数据层：内容进不了索引，后面永远召回不了**

- 结构感知切分 + parent/child 两级：child 小而准做检索单元，切太碎会把答案的关键限定条件切散，切太大语义被稀释
- 表格整体保留、大表重复表头；句子按语义聚合而非字符硬切，配合 Overlap 减少跨 chunk 语义断裂
- 知识库覆盖治理：源文档缺失、互相矛盾时检索不可能凭空召回——靠评测集暴露缺口，倒逼文档治理

**2. 索引层：让同一内容有多个"被找到的入口"**

- 混合检索：向量 + BM25 双路并行——向量管语义泛化，BM25 管专有名词、错误码、型号的字面命中，互补单路盲区
- 标题/章节路径作为 chunk 语义前缀，给"指代不明"的片段补全上下文，改善向量表示
- Embedding 模型按业务语料实测，必要时领域微调，把相似对与不相似对的相似度分布拉开

**3. 查询层：改 query 比改检索更便宜**

- Query Analyzer：意图识别 + 关键条件提取，口语化 query 转成检索友好的形式并补充相关检索词
- 三种变换按需选用：Rewrite 指代消解成自包含查询；MultiQuery 宽泛问题扩展多个变体并行召回、变体间再做一层 RRF；HyDE 用假设答案弥补 query 与文档的语义鸿沟

**4. 参数层：召回率与精度的旋钮**

- 放宽 top-K 和每路候选数：K 越大召回率越高，多召回的噪声交给 Reranker 精排和上下文预算控制
- 相似度阈值别定太严：阈值本质是"精度换召回"的开关，宁可多召回一些再靠精排过滤

**5. 闭环验证：提召回不能以牺牲精度为代价**

- 每项改动都在同一套 Golden Dataset 上回归：盯 Recall@K 提升的同时看 Context Precision / Faithfulness 有没有回退，防止"召回提了、噪声多了、答案反而变差"

结合本项目：混合检索、Query 变换、两级切片已覆盖 1~3 层；参数层（K 值、阈值）是最便宜、见效最快的调优入口，但必须走回归门禁。

### 8. 如何提高 Hit Rate@K、MRR@K、NDCG@K？

**先分清两类指标：Hit Rate / Recall 是"召回"指标——相关 chunk 进没进前 K；MRR / NDCG 是"排序"指标——进来的排得高不高。没进候选池的结果不可能被排上去，所以先提 Hit Rate，再提 MRR / NDCG。**

**诊断方法：看 gold chunk 的排名分布，对症下药**

- gold chunk 排在 K 名之外（Hit Rate 低）→ 召回问题，用第 7 问的数据/索引/查询层手段
- gold chunk 在候选池内但排名靠后（MRR 低）→ 排序问题，重点做精排
- 命中了但多个相关块只有少数进前列（NDCG 明显低于 Hit Rate）→ 多证据覆盖与多样性问题

**1. 提高 Hit Rate@K：扩大候选覆盖**

- 手段与第 7 问一致：混合检索、Rewrite / MultiQuery / HyDE、parent/child 切片、调大 K、换更强的 embedding 模型
- 专门盯 0 命中查询：逐条归因——query 表达问题走 Query 变换，知识库缺失走文档治理，检索层无解

**2. 提高 MRR@K：把首个相关结果顶到最前面**

- Reranker 精排：cross-encoder（如 bge-reranker）或 LLM-as-Reranker 对 top 候选重打分，是提升 MRR 最直接的手段
- RRF 融合调参：k 值、两路候选数配比，决定两路结果的相对权重
- 匹配增强：chunk 带标题/章节语义前缀，让排序模型"看懂"片段主题；embedding 微调加入难负例（hard negatives），让"相似但不相关"的排不上去
- 近重复去重：重复内容霸占前排位置，会把首个相关结果挤到后面

**3. 提高 NDCG@K：多个相关块要排得又全又高**

- NDCG 看分级相关性和位置折损，MRR 只看第一个相关结果——NDCG 上不去通常败在"多证据召回不全"
- MultiQuery 变体并行召回 + 变体间 RRF 融合：不同变体覆盖答案的不同侧面，把分散的相关块都拉进前列
- 同一 parent 的多个 child 相似度极高、重复占位——按 parent 分组去重或 MMR 多样性重排
- Reranker 用分级相关性标注微调，让"高相关"和"部分相关"区分开

**4. 闭环验证**

- 四个指标一起看：精排只在候选池内重排，提 MRR / NDCG 不会提高 Hit Rate 的上限；反之收紧 K 会同时压低所有指标——所有改动在 Golden Dataset 上回归，防止按下葫芦浮起瓢

## 三、效果优化与评估

### 9. 遇到过模型理解不对的情况吗？怎么解决的？

**定位思路**：不简单归因于模型能力不足，而是把问题拆成问题理解、证据检索、答案生成三个环节，先定位错误发生在哪一层，再针对性优化。

**1. 优化问题理解**

- 检索前增加 Query Analyzer，做意图识别和关键条件提取（加班类型、适用部门、审批条件等）
- 口语化问题（如"周末加班能不能调休"）转换成更适合检索的查询，并补充"加班审批""调休申请条件"等相关检索词

**2. 优化检索和上下文组织**

- 关键词检索 + 向量检索混合，RRF 融合结果，再用 Reranker 对候选文档做相关性排序
- 尽量保留规则的适用范围、例外条件和前置要求，避免只召回"加班可以调休"这类局部片段，却遗漏后面的限制条款

**3. 约束生成并建立评估机制**

- System Prompt 明确要求：只依据检索到的证据回答，区分一般规则和特殊规则；证据不足时明确说明，不允许自行补充制度
- 回答带引用编号，可追溯到原始文档和具体片段
- 用一组典型问题做回归测试，重点检查问题理解是否正确、相关证据是否召回、回答是否忠于证据；结合 Faithfulness、Recall@K 和人工抽检定位问题

### 10. 如何进行 RAG 调优？

核心原则：一切调优必须由评估体系驱动。分效果调优和性能调优两个层面。

**一、前提：先建评估体系，再谈调优**

- Golden Dataset：每条查询带黄金 chunk（goldChunkIds）和参考答案，数据集绑定 indexVersion 和 embeddingVersion
- 定义 8 项指标：检索侧 Recall@K / Hit Rate / MRR / NDCG；生成侧 Context Precision / Context Recall / Faithfulness / Answer Relevance
- 回归门禁：每次调参跑评估，任一指标低于基线 ×(1−0.1) 即 FAIL，产出 Markdown 报告阻断合并——保证调优不会"按下葫芦浮起瓢"

**二、效果调优：按数据流水线逐层优化**

1. **切分层（影响最大的第一步）**
    - Parent-Child 两级分块：child 400 字符做检索单元（小而准），parent 2000 字符做上下文单元（大而全），child 带 80 字符 overlap；命中 child 后回填 parent 给 LLM，兼顾检索精度和上下文完整性
    - 结构感知切分：Markdown 按标题分节、标题作语义前缀；表格和代码块整体保留绝不拆散；按句子聚合而非字符硬切，避免句子截断
    - chunk 用内容哈希做稳定 ID，幂等落库，支持增量更新
2. **召回层：混合检索解决单路召回盲区**
    - 向量（Qdrant Cosine）+ 关键词（OpenSearch BM25）双路并行：向量管语义泛化，BM25 管专有名词/精确匹配（向量对代码标识符、型号这类 token 很弱）
    - RRF 融合（k=60）做去量纲合并，不依赖两路分数可比
    - 每路 3 秒竞速超时，关键词路挂了降级纯向量，保证可用性
    - metadata 过滤三重保障：Qdrant payload filter + OpenSearch terms filter + 回表二次校验，多租户/多版本不会串数据
3. **查询智能层：改 query 而不是只改检索**
    - Query Analyzer → Router → Transform 管线，规则优先（cheap-first，零 LLM 开销），低置信才升级 LLM
    - 三种变换互斥、按需选用：Rewrite（指代消解，把"它怎么样"改写成自包含查询）、MultiQuery（宽泛问题扩展 3 个变体并行召回，变体间再做一层 RRF）、HyDE（多跳/概念性问题生成假设答案去检索，弥补 query 与文档的语义鸿沟）
4. **重排层：精排解决"召回对但排序差"**
    - RRF 融合后用 LLM-as-Reranker 对候选重排序（接口抽象成 Reranker，可平滑换 bge-reranker/Cohere）
    - 省 token：少于 4 条证据跳过重排
5. **生成层：防幻觉 + 上下文工程**
    - 单证据截断 1500 字符、上下文总预算 8000 字符，控制噪声
    - System Prompt 强约束"仅依据证据回答，证据不足明确说明"；回答带 [1][2] 编号引用回链到具体 chunk，用 Faithfulness 指标闭环验证
6. **必要时上 GraphRAG**
    - 实体关系/多跳类问题路由到 Neo4j 做 N-Hop 子图遍历或社区摘要全局检索
    - 不是所有查询都进图，由 Router 按意图路由，避免图检索的高成本

**三、性能调优：一个真实案例**

- 压测发现 /search 平均 13.45s（检索 5.76s + 生成 7.69s），针对性优化：
    - MultiQuery 的多次 embedding 批量合并为 1 次 API 调用（原来 N 次串行）
    - 重排统一为 1 次
    - 收紧上下文预算 + maxTokens 1024
    - Redis 语义结果缓存（TTL 600s，documentIds 进缓存键，防版本切换命中旧答案）
- 结果：简单查询降到 2~4s，重复命中缓存约 5ms

**四、工程兜底（区分玩具和生产的部分）**

- PostgreSQL 是唯一事实源，Qdrant/OpenSearch/Neo4j 全是可重建的派生索引——换 embedding 模型、改 chunk 策略后可全量重索引
- Outbox 事件 + Reconciliation 对账循环保证索引最终一致，消费失败自愈
- 全链路降级：LLM 挂了回退确定性实现，图检索挂了降级无子图

### 11. 评测集的标准答案是怎么来的？

来源：真实业务问题抽样 + 依据原始文档人工标注 + 双人复核。

1. 从客服咨询、员工提问记录、历史搜索日志中收集问题；历史数据不足时，由业务人员根据制度文档补充典型问题
2. 由熟悉业务的人员对照原始制度，记录正确答案、对应的文档和章节，以及能够支持答案的标准证据片段
3. 容易混淆、涉及多个制度或存在版本差异的问题，由第二位审核人员复核；无法从文档确认的问题标记为"证据不足"，不强行编造答案
4. 固定问题、标准答案、标准证据和文档版本；后续调整 Chunk 大小、检索算法、Reranker 或 Prompt 时，使用同一套评测集进行对比

### 12. 召回的数据互相冲突怎么办？

**先分清是"伪冲突"还是"真冲突"：伪冲突靠检索和上下文工程修，真冲突靠版本过滤 + 生成约束 + 文档治理兜底，最后用评测集闭环。**

**第一步：定位冲突类型——很多"冲突"不是数据问题**

1. **切片伪冲突**：答案的限定条件（适用部门、生效日期、例外条款）被切散，两条 chunk 各带半截规则，拼起来"看似矛盾"——不是数据冲突，是局部片段问题，靠保留适用范围/例外条件、命中 child 回填 parent 解决
2. **版本冲突**：新旧版制度同时在线——是版本过滤没做好，不是文档问题
3. **真冲突**：源文档本身互相矛盾（多部门发文口径不一）——真正的数据治理问题

**第二步：分层处理**

1. **检索层硬过滤（伪冲突 + 版本冲突在这一层消灭）**
    - versionId、生效日期、适用范围做成 metadata 硬过滤条件，配合回表二次校验——检索前就把旧版本和不适用范围的 chunk 排除，LLM 根本看不到冲突
    - 语义缓存键带 documentIds，防止版本切换后命中旧答案
2. **生成层约束（真冲突到了 LLM 面前时的兜底）**
    - System Prompt 明确要求：证据之间存在冲突时不得擅自取舍，必须指出冲突并分别引用 [1][2] 出处，标注生效时间和适用范围的差异
    - 排序时把生效日期新、来源权威性高的证据往前放（Reranker 或规则加权），让 LLM 优先采信
3. **数据治理层（治本）**
    - 上传/更新文档时做冲突检测：与已有文档主题和实体高度重叠的 chunk 做比对，疑似矛盾进人工审核队列，确认后旧版本下架——保证"同一问题单一有效版本"
    - 明确文档权威性规则：哪个来源说了算、新版本生效旧版本是否作废，入库时就定好
    - RAG 忠实检索错误知识、不会自动纠错——冲突靠评测集暴露：Golden Dataset 专门放已知矛盾的 case

**闭环验证**：冲突处理的所有改动（过滤规则、Prompt 约束、排序加权）都在同一套 Golden Dataset 上回归，把"冲突识别率"和 Faithfulness 一起盯，防止修了冲突伤了其他指标。

**结合本项目**：版本过滤和缓存键已覆盖版本冲突；生成约束"仅依据证据回答 + 引用可溯源"天然支持"呈现冲突而非编造答案"；缺口在上传侧冲突检测和 Golden Dataset 的冲突 case，属于文档治理的延伸。

## 四、性能优化

### 13. 有没有延迟特别高的场景？如何解决？

**定位：用数据说话**

- 给 /search 链路打点，latencyMs、retrievalMs、generationMs 落在 retrieval_logs 表
- 压测发现 P50 是 13.45 秒：检索 5.76s + 生成 7.69s
- 拆开看根因：数据库和向量索引都不慢，慢在一次请求里串行了 4~6 次外部 LLM/API 调用，每次火山方舟往返 1~3 秒，叠加出来的

**三个最慢场景**

1. Multi Query：宽泛问题扩展成 N 个变体，原实现是每个变体各付一次 embedding、各做一次 LLM 重排、各开一个回表事务，N 倍放大
2. 低置信查询：规则路由判低置信后，要先调 LLM Analyzer 再调 LLM Router，两次串行往返之后才真正开始检索
3. 长尾没兜底：LLM 重排没有容错，一失败整个请求 500；检索超时配置声明了但没生效，下游一慢就无限等；生成段没上限没流式，用户干等

**解决方案：四层**

1. **削调用次数**：变体的 embedding 批量合并成一次；重排从每路一次改成 RRF 融合后统一一次；N 路召回不回表、融合后统一回表一次；Analyzer 和 Router 合并成一次 LLM 调用直接输出"分析+路由"——多查询场景从 2N 次调用降到常数次
2. **削单次开销**：证据截断加总预算控制 prompt 大小，max_tokens 限输出；Redis 结果缓存，重复查询 5 毫秒返回
3. **削长尾**：每路检索加竞速超时，3 秒降级——向量路超时就退纯关键词，反过来也一样；重排失败降级到本地确定性重排。保证下游故障时是"变慢"而不是"雪崩"
4. **削感知延迟**：规划中的流式输出——检索完先把引用推给前端，答案流式吐，总耗时不变但首屏从 8 秒变 2 秒

**效果与方法论**

- 简单查询从 13.45s 降到 2~4s
- 方法论：cheap-first——能用规则的不用 LLM，能合并的调用不串行，所有优化都有打点数据可以回归验证

## 五、工程化与部署

### 14. RAG 系统在实际部署中可能面临哪些挑战？

**核心矛盾：LLM 的输出不确定性 vs 生产系统对准确、可控、可审计的要求。挑战贯穿数据、检索、生成、工程、安全全链路。**

**一、数据侧：垃圾进，垃圾出**

- 解析难：扫描件、表格、图片、复杂版式，解析错了后面全错——先版面分析和内容类型识别，OCR + 多模态兜底
- 切片两难：切太碎丢上下文，切太大检索不准——结构感知切分 + parent/child 两级
- 知识更新：文档频繁改版，新旧答案混杂、重复内容干扰——内容哈希幂等 + 版本管理 + 全量重索引能力
- 源数据有错或互相矛盾：RAG 会忠实检索错误知识，不会自动纠错——依赖上游文档治理，靠评测集暴露

**二、检索侧：召回不准，全盘皆输**

- 单路盲区：向量对专有名词弱，BM25 对同义改写弱——混合检索 + RRF + Reranker
- query 质量：口语化、指代、多跳问题直接检索必失败——Query Analyzer / Rewrite / MultiQuery / HyDE
- 上下文预算：召回太多是噪声，太少证据不足——单证据截断 + 总预算 + 精排

**三、生成侧：幻觉与可信**

- 幻觉：证据不足时模型倾向编造——Prompt 强约束"仅依据证据回答"、证据不足明确说明、Faithfulness 指标闭环
- 不可溯源：用户不敢信——引用编号回链原始 chunk 和文档
- 版本错乱：答案停留在旧版制度——答案绑定索引版本，切换版本即时生效

**四、工程侧：区分玩具和生产线的部分**

- 延迟：一次请求串行 N 次 LLM/API 调用，延迟线性叠加——调用合并、结果缓存、竞速超时、流式输出
- 一致性：文档更新后索引不同步，检索到已删除内容——Outbox 事件 + 对账循环保证最终一致
- 可用性：外部依赖一挂就雪崩——全链路降级：向量路超时退关键词、重排失败退本地排序、LLM 挂了退确定性实现
- 可演进：换 embedding、改切片策略要平滑迁移——唯一事实源 + 派生索引可全量重建 + Golden Dataset 回归验证
- 成本：token 费用随 QPS 线性增长——cheap-first 规则优先、语义缓存、prompt 预算控制

**五、安全与合规**

- 多租户权限：不能指望 LLM 自觉不越权——检索层强制 metadata 过滤 + 回表二次校验
- 数据出域：敏感文档不能发给外部 API——本地模型或私有化部署
- Prompt 注入：文档或 query 里藏恶意指令——证据与指令分离、输入输出过滤
- 审计：答案错了要能追责——全链路引用回链 + 检索日志落库

**六、效果评估：最大的挑战是"不知道做得好不好"**

- 没有评估体系，所有调优都是盲调——先建 Golden Dataset + 双侧指标 + 回归门禁，一切改动由评估驱动

**收尾**：这些挑战几乎没有一个是"换个更强的模型"能解决的，都要靠工程手段——评估、降级、缓存、可重建索引——把不确定性框在可控范围内。
